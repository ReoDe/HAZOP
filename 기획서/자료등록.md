# 자료 등록 기획

[상세 플로우차트](<../flow chart/01-registration.md>) · [전체 기획](전체기획.md)

## 목적과 구현 범위

사용자가 P&ID 파일을 제공하면 원본과 식별정보를 보존하고, 정보 추출 단계에서 동일 원본·버전을 다시 참조할 수 있게 합니다. 첫 구현은 파일 한 개씩 처리하며, 등록 목록과 메타데이터의 수동 수정도 지원합니다.

현재는 기획 초안이며 등록 코드와 UI는 미구현입니다. 도면 기호·배관 추출, 노드 생성·편집, 그래프 통합은 이 단계의 범위에 포함하지 않습니다. 전체 시스템의 수동 노드 편집 요구는 유지합니다.

## 결정 상태

| 항목 | 상태 |
| --- | --- |
| 첫 입력 | FreeCAD 또는 draw.io로 만든 P&ID 원본 한 개. 객체·문서·페이지 참조를 보존 |
| 지원 형식 | 사용자 변경 결정: FreeCAD(.FCStd) 또는 draw.io(.drawio) 원본을 첫 대상으로 고려. PDF·PNG·JPG는 후속 지원 대상 |
| 입력 방식 | 사용자 결정: 간단한 웹 화면에서 파일 선택 또는 드래그 앤 드롭. 두 방식은 같은 Python 등록 처리 사용 |
| 도면 번호·개정번호 누락 | 미확인 상태로 등록 가능. 내부 ID와 등록 버전으로 원본을 구별 |
| 저장 방식 | 원본 파일과 구조화된 등록정보를 보관. 저장 기술은 구현 시 선택 |

사용자 결정으로 표시되지 않은 항목은 이번 초안의 제안이며 실제 사용 과정에서 조정할 수 있습니다.

장기적으로는 P&ID의 여러 자료형(PDF의 벡터·스캔·혼합 형태, 다양한 이미지, CAD 원본, 구조화된 설계 데이터)을 모두 고려합니다. 첫 지원 대상은 FreeCAD·draw.io 원본으로 변경하며, 기타 형식의 지원은 이후 구체화합니다. 자세한 기록은 [정보 추출 기획](정보추출.md)에 둡니다.

## 첫 등록 화면

1. 프로젝트와 자료 종류(P&ID)를 선택합니다.
2. FreeCAD 또는 draw.io 원본 파일 한 개를 선택하거나 업로드 영역에 드래그 앤 드롭합니다. 여러 파일을 놓으면 한 개씩 등록하도록 안내합니다.
3. 파일명·형식·문서/객체/페이지 정보와 가능한 미리보기를 표시하고, 도면 번호·개정번호·제목을 입력하거나 미확인으로 둡니다. 원본 형식별 미리보기 방법은 실제 샘플로 확인하고, 렌더러 미지원과 원본 읽기 실패를 구분합니다.
4. 등록을 실행하면 진행 상태와 중복·충돌·오류를 표시합니다. 자동 중복 확인 시점에 따라 기존 자료 안내가 먼저 나타날 수 있습니다.
5. 성공하면 자료 ID·등록 버전·미확인 항목과 등록 목록을 보여줍니다. 실패 시 원인과 재시도 경로를 안내합니다.

화면은 파일 선택과 정보 입력을 담당하고, 실제 형식·중복·무결성 검증은 Python에서 동일하게 수행합니다. 미리보기 파일은 파생 자료이며 원본을 대체하지 않습니다. 웹 프레임워크는 아직 정하지 않습니다.

## 입력과 등록정보

원본 설계자료 10종을 공통 등록 구조로 수용하되, 첫 구현의 검증 대상은 P&ID입니다. 자료 종류와 실제 파일 형식은 구분합니다.

| 항목 | 처리 방식 |
| --- | --- |
| 프로젝트 ID | 필수. 자료가 속한 프로젝트를 명시 |
| 자료 종류 | 첫 대상은 P&ID. 향후 PFD·운전조건 보고서 등으로 확장 |
| 내부 자료 ID·등록 버전 | 시스템 발급. 설계 문서의 개정번호와 구분 |
| 원본 파일명·저장 참조 | 원래 파일명 보존. 저장 시 파일명 중복으로 덮어쓰지 않음 |
| 실제 형식·크기·해시 | Python 자동 확인. 해시는 원본 식별과 무결성 확인에 사용 |
| 문서·객체·페이지 정보 | 형식별로 확인 가능한 객체·페이지 정보 기록. 없는 정보는 강제하지 않음 |
| 도면 번호·개정번호·제목 | 사람이 입력·수정. 알 수 없으면 미확인. 파일명만 보고 확정하지 않음 |
| 등록·변경 이력 | 등록자 또는 실행 주체, 시각, 변경 전후, 사유 |
| 상태·검증 결과 | 초안·보류·등록 완료·실패를 구분하고 미확인 항목과 문제 목록 기록 |

자동으로 읽은 파일 정보와 사람이 입력한 설계 식별정보를 구분합니다. 등록 단계의 자동 검증은 파일과 등록정보에 대한 검사이며, 도면 내용의 정확성이나 판독 품질을 보증하지 않습니다.

## 처리 원칙

1. 지원 형식, 실제 문서 열기, 형식별 객체·문서 구조 읽기를 검사합니다. 손상·빈 파일이나 암호로 접근할 수 없는 파일은 사유를 표시하고 완료 처리하지 않습니다.
2. 같은 프로젝트의 동일 해시 원본은 기존 등록을 안내하고 재사용합니다. 같은 파일명만으로 중복이라고 판단하지 않습니다.
3. 동일 도면 번호·동일 개정번호인데 파일 내용이 다르면 충돌로 보류합니다. 도면 범위와 식별정보를 사람이 확인하기 전 덮어쓰지 않습니다.
4. 도면 번호가 같고 개정번호가 다르면 별도 버전으로 보관합니다. 업로드 시각만으로 최신 설계라고 판단하지 않습니다. 개정번호가 미확인이면 내부 버전만 발급하고 새 설계 개정으로 단정하지 않습니다.
5. 원본 파일은 변경하지 않습니다. 추후 회전·해상도 보정이나 페이지 렌더링이 필요하면 별도 파생 파일과 원본 참조를 만듭니다.
6. 메타데이터 수정은 허용하되 이력을 남기고 충돌 검증을 다시 수행합니다. 원본 교체는 기존 파일 덮어쓰기 대신 새 등록 버전으로 처리합니다.
7. 원본 저장 후 해시와 참조를 확인한 뒤 완료 상태로 전환합니다. 저장 중 실패하면 미완료 상태와 원인을 남기고 재시도로 중복이 생기지 않게 합니다.
8. 실제 원본은 실행 환경의 자료 저장 공간에 보관하도록 구상합니다. GitHub의 기획 문서 폴더를 원본 파일 저장 위치로 가정하지 않습니다.

## 정보 추출 단계에 전달할 내용

자료 ID, 등록 버전, 프로젝트, 자료 종류, 실제 파일 형식, 원본 파일 참조, 해시, 페이지 정보, 입력된 도면 번호·개정번호와 미확인 항목을 전달합니다. 등록 완료는 정보 추출 시작의 전제이며, 등록만으로 추출을 자동 실행할지는 추출 단계 기획에서 정합니다.

## 독립 검증

샘플 파일과 임시 저장 공간·등록 목록을 이용해 이 단계만 검증합니다. 도면 인식 모델·정보 추출 코드·통합 그래프·AI는 필요하지 않습니다.

| 사례 | 기대 결과 |
| --- | --- |
| 지원 형식의 정상 P&ID | 원본·ID·해시·등록정보 저장, 다음 단계 참조 생성 |
| 파일 선택과 드래그 앤 드롭으로 각각 등록 | 동일한 Python 검증과 등록 결과, 입력 방식별 검증 누락 없음 |
| 여러 파일을 한 번에 드롭 | 한 개씩 등록하도록 안내, 일부만 조용히 등록하지 않음 |
| 손상·빈 파일·접근 불가 파일 | 사유 표시, 등록 완료와 추출 전달 금지 |
| 확장자와 실제 형식이 다름 | 불일치 표시, 지원 여부 확인 전 완료 금지 |
| 같은 프로젝트에서 동일 원본 재등록 | 기존 참조 재사용, 중복 등록 생성 금지 |
| 같은 파일명에 내용은 다름 | 파일명만으로 병합하지 않고 각각 식별 |
| 같은 도면·개정번호에 서로 다른 내용 | 충돌 보류, 기존 원본 유지 |
| 같은 도면의 다른 개정번호 | 원본별 버전 분리, 이전 버전 추적 가능 |
| 도면 번호·개정번호를 모름 | 내부 ID로 등록하고 미확인 상태 전달 |
| 식별정보 수동 수정 | 변경 이력 보존, 중복·개정 충돌 재검증 |
| 원본 저장 실패 또는 저장 후 해시 불일치 | 실패·미완료 기록, 추출 전달 금지, 재시도 시 중복 방지 |

### 통과 기준

원본 읽기와 지원 형식 확인, 필수 시스템 정보 생성, 저장 후 무결성 확인, 유효한 참조 생성이 완료되어야 합니다. 해결되지 않은 식별 충돌이 없어야 하며, 도면 번호 등 미확인 사항은 명시적으로 전달해야 합니다. 생성된 등록정보와 원본으로 동일 입력을 재현할 수 있어야 합니다.

## 다음 작업

입력 형식과 방식은 확정했습니다. 최소 등록정보 예시, 웹 화면과 Python 등록 처리 사이의 인터페이스, 저장 위치를 정한 뒤 등록 기능과 위 검증 사례를 구현합니다. 이후 정보 추출 상세 흐름으로 진행합니다.
