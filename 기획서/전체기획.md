# 전체 기획

[프로젝트 소개](../README.md) · [최상위 플로우차트](<../flow chart/00-overview.md>)

## 목적

설계도면과 문서에 흩어진 설비·연결·운전조건·보호수단 정보를 통합하고, 원본 근거를 추적할 수 있는 전문가 검토용 HAZOP 초안을 만드는 것을 목표로 합니다.

## 전체 구성

1. 자료 등록: 도면·표·문서의 원본과 버전을 관리합니다.
2. 정보 추출: 자료 유형에 맞는 스크립트로 대상, 관계, 값과 조건을 추출합니다.
3. 정보 통합·관리: 추출 결과를 공통 구조로 모으고 동일 대상 연결과 검증을 수행합니다.
4. [HAZOP 분석](HAZOP분석.md): 선택 구간의 정상 운전부터 편차별 경로를 탐색하고 AI가 해석·가설·위험도를 제안합니다. 전체 후보와 선택·제외·보류 판단을 저장합니다.
5. [검토·결과 관리](검토결과관리.md): 편차 목록과 도면·근거를 함께 검토하고 편차별 확정합니다. 개선 조치·자료 요청 메모를 구분하며, 구간 전체 재검토와 화면·Excel 출력을 관리합니다.

## 공통 원칙

- 도면마다 변환 방식이 달라도 결과는 공통 형식으로 연결합니다.
- 문서 사이의 링크와 함께, 문서가 설명하는 대상과 사실을 연결합니다.
- 추출한 정보에는 원본 파일·버전·페이지·영역 또는 문장 등의 근거를 남깁니다.
- 동일 태그라도 프로젝트와 공정 맥락을 확인하여 대상을 식별합니다.
- 미확인 값과 상충하는 정보를 임의로 확정하거나 덮어쓰지 않습니다.
- 그래프의 개별 설비 노드와 HAZOP의 검토 구간은 구분합니다.
- 위키·Markdown은 읽기와 기획에 활용하며, 분석에 필요한 값과 관계는 구조화합니다.
- 자료 등록·추출·통합은 Python 자동 처리를 기본으로 합니다. AI는 HAZOP 단계의 그래프 기반 추론에 주로 사용하며, 앞 단계에서는 불만족스러운 결과의 선택적 검수·보정에 활용할 수 있습니다.
- 사람의 수동 노드 생성·수정·연결을 지원하고, 자동 처리 결과와 동일한 검증을 적용합니다.
- 각 상세 흐름은 다른 단계나 AI 없이도 샘플 입력으로 독립 검증할 수 있도록 입력·출력·검증 기준을 정의합니다.
- 대화 중 기억할 미구현 요구사항은 [메모리](../메모리/README.md)에 누적하고, 구현 및 검증이 확인되면 해당 항목을 삭제합니다.

## 통합 예시

### 원본 설계자료의 활용

모든 자료는 등록 후 추출 대상이 되며, 아래는 추출·통합·분석에서 각각의 역할입니다.

| 원본 자료 | 추출 내용 | 통합 대상 | HAZOP 활용 |
| --- | --- | --- | --- |
| 공정 설계 의도 및 설명서 | 목적·역할·정상 운전 설명 | 공정·설비·운전모드 | 설계 의도와 검토 구간 |
| PFD 및 물질·열수지 | 흐름·스트림·유량·조성·열량 | 설비·스트림·물질 | 정상 흐름과 이탈 영향 |
| P&ID | 기호·태그·배관·계기·연결 | 설비·포트·배관·제어 관계 | 원인·영향 경로 |
| 물성·위험성 자료 | 물성·독성·인화성·반응성·혼합 금기 | 물질·취급 구간 | 누출·화재·독성·반응 결과 |
| 운전조건 및 허용 한계 | 정상 범위·운전 한계·설계 한계 | 설비·배관·운전모드별 조건 | 편차와 한계 초과 |
| 주요 기기·배관 설계 사양 | 용량·재질·등급·성능 | 설비·배관 | 한계와 손상 가능성 |
| 제어·경보·인터록 설계 | 측정값·설정값·조건·동작 | 계기·제어 대상·차단 대상 | 제어 실패와 보호 기능 |
| 압력 방출 및 비상 배출 설계 | 설정압력·용량·방출 경로 | 보호장치·보호 대상·배출처 | 과압 보호와 방출 영향 |
| 운전모드 및 주요 운전 절차 | 작업 순서·전환 조건·격리 방식 | 운전모드·설비·작업 | 기동·정지·정비 중 편차 |
| 유틸리티 및 외부 연결 조건 | 공급 조건·의존 관계·외부 접속 | 공급원·사용 설비·외부 시스템 | 공급 상실과 상·하류 영향 |

자료 종류와 파일 형식은 구분합니다. 한 자료에 도면·표·설명문이 함께 있으면 각 부분에 적합한 추출 방식을 적용합니다. 통합 단계의 직접 입력은 그 추출 결과이며, 원본은 검수와 추적을 위한 근거로 유지합니다.

### 동일 대상 연결 사례

아래 태그와 수치는 구조 설명을 위한 가상 예시입니다.

| 원본 자료 | 추출할 정보 | 통합 방식 |
| --- | --- | --- |
| P&ID | P-101과 V-101의 연결 | 설비 사이의 배관 연결로 저장 |
| 운전조건 보고서 | V-101의 정상 운전압력 5 bar | V-101의 운전조건으로 연결 |
| 인터록 설명서 | V-101 압력이 8 bar 이상이면 P-101 정지 | 적용 조건과 정지 동작을 관련 설비에 연결 |

각 사실의 원문 근거는 별도로 유지합니다. 문서별 정보 열람과 설비별 정보 열람이 모두 가능하도록 구상합니다.

## 노드·관계·속성 정의 관리

현재는 [정보 통합·관리 기획](정보통합관리.md)의 정의 초안에서 종류와 속성, 필요한 이유 및 예시를 관리합니다. 실제 자료를 보며 항목을 추가하고 미정 사항을 구체화합니다. 향후 규모가 커지면 별도 데이터 사전으로 분리하고, 구현 시 Python이 검사할 수 있는 JSON Schema 등의 정의와 연결합니다.

정의에는 이름·의미·적용 대상·자료형·단위·필수 여부·허용값을 포함합니다. 원문 출처·버전·검토 상태는 노드뿐 아니라 개별 사실과 관계에도 연결할 수 있어야 합니다.

## 첫 개발 범위

첫 구현 단위는 [자료 등록](자료등록.md)입니다. FreeCAD 또는 draw.io로 직접 만든 P&ID 원본을 받아 원본과 식별정보를 저장·검증합니다. 이후 한 장의 작은 구간에서 기호·태그·배관과 연결을 추출하고, 원본과 대조하여 사람이 수정·확정하는 편집기로 확장합니다. 다음으로 운전조건 문서 하나를 연결해 도면과 문서의 통합을 검증합니다.

## 단계 간 데이터 규격 초안

이 절을 ①~⑤가 공유하는 ID·버전·상태·변경 알림의 기준으로 사용합니다. 아래 JSON은 가상 자료의 최소 전달 예시이며 실행 코드·완전한 JSON Schema·DB 테이블 정의가 아닙니다. 실제 필수 필드와 저장 기술은 구현 전 샘플로 구체화합니다.

### 식별자와 버전

| 필드 | 의미 |
| --- | --- |
| `schema_version`, `project_id` | 전달 형식 버전과 프로젝트. 모든 단계 기록에 포함 |
| `material_id`, `registration_version` | 자료와 등록 스냅샷. 설계 문서의 개정번호와 구분. 원본·메타데이터 변경 시 새 버전 |
| `extraction_run_id`, `local_id` | 추출 실행과 그 실행 안의 임시 노드·관계. 원본 객체 ID와 구분 |
| `graph_id`, `graph_version`, `entity_id` | 통합 그래프 스냅샷과 통합 대상. 각 대상의 원본·임시 ID 대응을 유지 |
| `region_id`, `region_version` | HAZOP 검토 구간과 설계 의도·경계·운전모드의 스냅샷 |
| `analysis_run_id`, `candidate_id`, `scenario_id` | 분석 실행, 편차 후보, 원인·결과 시나리오 |
| `review_id`, `review_version` | 전문가 검토본. AI 원안·이전 검토본과 별도 보존 |
| `event_id` | 변경 알림의 고유 ID. 같은 알림 재수신 시 재검토 이력을 중복 생성하지 않도록 사용 |

버전 참조는 ID와 버전의 쌍으로 고정하며 실행 중 최신 버전으로 자동 치환하지 않습니다. 해시는 파일 무결성 확인용으로, 메타데이터 버전이나 전체 그래프 버전을 대신하지 않습니다. 태그·파일명·도면 개정번호만으로 내부 ID를 대체하지 않습니다. 원본 객체 ID도 자료·등록 버전·문서/페이지 범위 안에서 해석합니다.

### 상태는 역할별로 구분

| 종류 | 필드와 값 예시 | 의미 |
| --- | --- | --- |
| 구조 검증 | `validation.status`: `passed`, `blocked` | 필수 형식·참조·제약 검사. `passed`여도 미확인 값이 있을 수 있음 |
| 미확인 정보 | `validation.unknowns` | 대상·항목·사유가 있는 목록. 차단 오류는 `blockers`에 따로 기록 |
| 정보의 확인 수준 | `knowledge_status`: `confirmed`, `unknown`, `hypothesis` | 원문/검토에서 확인한 정보, 미확인 정보, 추론 가설 구분. 모든 공학적 정확성을 보증하지 않음 |
| 후보 판단 | `selection_status`: `selected`, `excluded`, `deferred` | 선택·제외·보류. 판단 주체·이유·시각을 별도 이력으로 유지 |
| 전문가 검토 | `review_status`: `not_reviewed`, `reviewing`, `deferred`, `confirmed` | 미검토·검토 중·보류·확정. 후보 판단과 독립 |
| 위험도 | `risk_proposal.status`: `proposed`, `deferred`; `risk_confirmation` | AI 제안 또는 보류와 사람의 확정값을 분리 |
| 재검토 | `review_required` | 해당 입력 버전에 대한 재검토 필요 여부. 과거 확정본을 삭제하지 않음 |

미확인 값은 `null`과 확인 상태·사유로 표현하며 0·안전·없음으로 바꾸지 않습니다. 해당 없음과 미확인도 구분하여 사유를 남깁니다. 구조 검증을 통과하지 못한 변경은 초안으로 보존하고 ④의 정상 그래프 관계에 합치지 않습니다. 개선 조치의 상태는 별도 관리하며 자료 요청 메모에 조치 상태를 강제하지 않습니다.

### ① → ②: 등록 원본 참조

```json
{
  "schema_version": "0.1",
  "project_id": "project-001",
  "material_id": "material-001",
  "registration_version": 1,
  "format": "drawio",
  "storage_ref": "originals/material-001/1/sample.drawio",
  "drawing_number": null,
  "design_revision": null,
  "documents": [{"document_id": "document-001", "page_ids": ["page-001"]}],
  "validation": {
    "status": "passed",
    "blockers": [],
    "unknowns": [{"field": "design_revision", "reason": "미확인"}]
  }
}
```

저장 시 파일 해시는 등록정보에 보관합니다. `storage_ref`는 예시 저장 키이며 실제 파일이나 외부 URL이 아닙니다. FreeCAD는 `format`을 `freecad`로 하고 페이지가 없으면 `page_ids`를 빈 목록으로 둡니다. ①은 문서·페이지 식별정보를 주고 ②가 실제 객체를 읽어 원본 참조를 완성합니다.

### ② → ③: 추출 결과와 원본 객체 근거

```json
{
  "schema_version": "0.1",
  "project_id": "project-001",
  "extraction_run_id": "extract-001",
  "source": {"material_id": "material-001", "registration_version": 1},
  "nodes": [
    {"local_id": "local-001", "kind": "tank", "tag": "T-101", "source_object_id": "cell-001"},
    {"local_id": "local-002", "kind": "valve", "tag": "V-101", "source_object_id": "cell-002"}
  ],
  "relations": [{
    "local_id": "local-edge-001",
    "kind": "physical_connection",
    "from": "local-001",
    "to": "local-002",
    "source_object_id": "edge-001",
    "flow_direction": null
  }],
  "source_context": {"document_id": "document-001", "page_id": "page-001"},
  "source_locations": [{
    "object_id": "cell-001",
    "coordinate_space": "page_local_2d",
    "unit": "canvas_unit",
    "bbox": [100, 100, 80, 60],
    "preview_transform_ref": null
  }],
  "validation": {
    "status": "passed",
    "blockers": [],
    "unknowns": [{"target": "local-edge-001", "field": "flow_direction", "reason": "원본에 흐름 방향 지정 없음"}]
  }
}
```

`from`·`to`는 접속 끝점의 나열이며 흐름 방향의 확정이 아닙니다. 예시는 설비 단위 연결이며 포트를 식별할 수 있는 경우 포트 ID를 끝점으로 사용합니다. `source_locations`는 위치 표기 예시만 담았으며, 객체 ID 자체가 근거 참조가 됩니다. 좌표가 없는 객체에는 빈 좌표를 만들어 넣지 않습니다.

원본 참조는 `source`·`source_context`·`source_object_id`를 합쳐 식별합니다. draw.io는 2차원 캔버스, FreeCAD는 페이지 없는 문서의 객체와 필요 시 `document_local_3d` 좌표·`mm` 등의 명시적 단위를 사용합니다. FreeCAD의 3차원 위치를 페이지 좌표로 오인하지 않게 하며 미리보기 투영이 있으면 변환 참조를 남깁니다. 원본 객체의 이름만으로 재추출 간 동일성을 보장하지 않습니다.

### ③ → ④: 검증된 그래프 버전

```json
{
  "schema_version": "0.1",
  "project_id": "project-001",
  "graph_id": "graph-001",
  "graph_version": 1,
  "input_runs": ["extract-001"],
  "entity_mapping": [
    {"extraction_run_id": "extract-001", "local_id": "local-001", "entity_id": "entity-001"},
    {"extraction_run_id": "extract-001", "local_id": "local-002", "entity_id": "entity-002"},
    {"extraction_run_id": "extract-001", "local_id": "local-edge-001", "entity_id": "relation-001"}
  ],
  "validation": {
    "status": "passed",
    "blockers": [],
    "unknowns": [{"target": "relation-001", "field": "flow_direction", "reason": "흐름 방향 미확인"}]
  }
}
```

그래프 본문과 원문 근거는 이 ID·버전으로 참조합니다. ④는 버전을 고정하고 관련 운전조건·물질·보호수단의 확인 여부를 추가 점검합니다. `passed`만 보고 자료가 완전하거나 모든 경로의 방향이 확정됐다고 판단하지 않습니다.

```json
{
  "schema_version": "0.1",
  "project_id": "project-001",
  "analysis_run_id": "analysis-001",
  "graph_ref": {"graph_id": "graph-001", "graph_version": 1},
  "region_ref": {"region_id": "region-001", "region_version": 1},
  "operating_mode": "normal",

    {"candidate_id": "deviation-001", "deviation": "유량 없음", "selection_status": "selected", "reason": "검토 대상으로 선택"},
    {"candidate_id": "deviation-002", "deviation": "역류", "selection_status": "deferred", "reason": "정상 흐름 방향 확인 대기"}
  ],

    "candidate_id": "deviation-001",

    "cause": "밸브 닫힘으로 인한 유량 상실 가능성",

```

후보의 판단 주체·시각·변경 이력, 실행 당시 설계자료·규칙·AI 입력/응답 기록은 연결된 실행 기록에 보관합니다. 후보·시나리오 ID는 실행에 소속되며 재분석 시 이전 ID 대응과 이력을 유지합니다. 위험도를 제안할 수 있는 경우에는 적용 기준표 버전·심각도·가능성·계산 결과·근거와 가정을 남깁니다. 예시는 기준표가 없어 위험도만 보류한 경우입니다.

### ⑤: 전문가 검토 기록

```json
{
  "schema_version": "0.1",
  "project_id": "project-001",
  "review_id": "review-001",
  "review_version": 1,
  "analysis_run_id": "analysis-001",
  "candidate_id": "deviation-001",
  "review_status": "deferred",
  "review_required": false,
  "risk_confirmation": null,
  "reviewer_id": "reviewer-001",
  "reason": "운전조건과 위험도 평가 기준 확인 필요",
  "action_ids": [],
  "material_request_memos": ["정상 유량과 위험도 기준표 확인"]
}
```

`review_required: false`는 변경에 따른 재검토 표시가 없다는 뜻이며 검토 확정을 뜻하지 않습니다. 실제 저장 시 검토 시각·시나리오별 수정 내용·메모 식별자와 변경 이력을 추가합니다. 확정 상태에는 사람의 위험도 판단과 적용 기준·근거를 남기되, 제외 후보처럼 위험도 비적용인 경우 비적용 이유를 명시합니다. 미확인 판단을 비적용으로 대체할 수는 없습니다.

### 변경 알림과 구간 전체 재검토

①의 등록 버전 변경은 `material_changed`, ③의 그래프 새 버전 발행은 `graph_changed` 알림으로 기록하는 방향입니다. 메타데이터 정정만인 경우도 변경 종류를 남겨 영향 범위를 검토합니다. 이 알림은 논리적 데이터이며 메시지 큐 등 특정 구현을 요구하지 않습니다.

```json
{
  "schema_version": "0.1",
  "project_id": "project-001",
  "event_id": "change-001",
  "event_type": "graph_changed",
  "subject": {"graph_id": "graph-001", "from_version": 1, "to_version": 2},
  "changed_entity_ids": ["entity-002"],
  "affected_region_ids": ["region-001"],
  "reason": "밸브의 연결 대상 수정",
  "review_scope": "all_candidates_in_affected_regions"
}
```

운전조건 변경은 원본 자료 또는 그래프의 변경으로 같은 참조 체계에서 추적합니다. `affected_region_ids`는 변경 대상과 원문 참조·구간 소속을 대조해 산정합니다. 해당 구간이 정해지면 바뀐 설비에 직접 연결된 편차만 좁히지 않고 **선택·제외·보류를 포함한 구간 전체 편차**에 재검토 표시를 생성합니다. 구간을 판별할 수 없으면 영향 범위 미확인으로 기록하고 사람이 확인할 때까지 영향 없음으로 처리하지 않습니다.

이전 확정본은 변경하지 않고 새 버전에 대한 재검토 기록을 덧붙입니다. 재분석 시 새 실행과 필요 시 새 구간 버전을 만들고 입력 버전을 다시 고정합니다. 과거 버전 조회나 같은 알림 재처리만으로 재검토 표시를 해소하지 않습니다.
