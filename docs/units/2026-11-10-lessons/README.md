# 2026-11-09~10 작업 묶음 교훈

작성 2026-11-10. 대상은 초기사건 P1~P3, 저장 결함 수정, AI 구독 연결 1·2, 데이터 일원화 C1~C7, APR1400 U0~U5, 기호 사전 1~3f·S5, 검토구간 분할 S1~S6, 성능 N2~N5다(`git log 2a84522~20..3ca0bba`, 51커밋). 오케스트레이터 세션 하나가 같은 체크아웃에서 하위 세션 약 20개를 지휘했다.

이 묶음에서는 기능보다 운영에서 시간을 더 많이 잃었다. 거짓 실패를 쫓고, 파일 차례를 기다리고, 기준값을 되돌리고, 보고를 기다렸다. 같은 일이 되풀이되지 않게, 사람이 기억해야 하는 규칙보다 스크립트·검사·기본값을 먼저 썼다. 문서로만 남긴 것은 아래 표에 '규칙'으로 표시했다.

## 방법

pstack `reflect` 절차를 따랐다. 대화 원문 23개(11-09 이후)에서 사용자 발화, 세션 간 메시지, 관련 키워드가 든 응답만 뽑아 요약본을 만들었다. 판단·도구·역방향 세 관점의 검토자가 그 요약본과 원문, 저장소를 대조했다. 종합은 별도 에이전트 없이 이 세션이 직접 했다. 세 보고가 대부분 같은 사건을 가리켰고, 반영 범위는 작업지시서에 이미 정해져 있었기 때문이다.

## 가장 중요한 다섯 가지

1. **시험 인터프리터가 하나로 정해져 있지 않아 거짓 실패를 몇 시간씩 쫓았다.** PATH의 `python`은 LibreOffice 내장 Python이다. `%LOCALAPPDATA%\HAZOP\venv-py312`에는 pdfplumber가 없다. 다 갖춘 것은 `~/.hazop/venv-py312` 하나다. 등록 화면 시험 4건이 '순수 HEAD에서도 실패'로 보고되어 총괄 보고까지 올라갔지만, 원인은 venv였다.
2. **회귀 기준값을 작업트리 코드로 갱신했다.** 기호 사전 세션이 자기 코드와 다른 세션의 채점 코드가 섞인 상태에서 `check_apr1400.py --update`를 돌렸다. 그 결과 HEAD 코드보다 높은 값이 기준이 되었다. 두 세션은 앞으로 조심하자고 약속했을 뿐 스크립트는 그대로였다.
3. **데스크톱 차례와 공유 파일 차례를 메시지로 넘겼다.** "써도 됨", "앞 메시지를 정정합니다", "반납" 같은 메시지가 오갔지만 키 입력은 Claude 창으로 새었다. 이것이 앱 결함으로 기록되기도 했다. `pdf_vector.py`는 하루에 1,466줄에서 2,265줄로 늘었고 11커밋이 들어갔다. 한 세션은 이 파일 차례를 한 시간 넘게 기다렸다.
4. **디스크를 아무도 세지 않았다.** 143쪽 추출이 35쪽에서 'No space left'로 멈췄다. 저장소 밖 시험 폴더가 15GB, `%TEMP%`의 hazop 임시 폴더가 3,000개(2.2GB)였고, 빈 `unk-*` 폴더도 2,100개 남았다. 누구 것인지 알 수 없어 지우지도 못했다.
5. **수치에 출처가 붙지 않았다.** 호출당 사용률 0.013%p와 0.027%p를 두고 한쪽이 '차단 결함'이 되었다. 둘 다 계정 전체가 함께 쓰는 계기로 잰 값이었다. 0.027%p는 다른 세션이 여럿 돌던 낮에 잰 것이다. APR1400 점수의 분모도 채점기를 고칠 때마다 269에서 293, 295로 바뀌었는데, 그사이 보고가 252/269, 276/293, 284/293으로 섞였다.

## 잘된 것 (지킬 것)

- **입력 확인이 붙은 톱니 기준값.** `check_apr1400.py`의 `ratchet()`은 입력 쪽 수와 대리 지표가 바뀌면 비교하지 않고 실패한다. 그래서 무인 실행이 '멈추고 보고'로 끝날 수 있었다. 단순하게 만든다고 이 확인을 빼지 않는다.
- **SNP 후퇴 0과 APR1400 점수를 함께 확인.** 한쪽 도면군만 좋아지고 다른 쪽이 나빠지는 일을 막았다.
- **측정하고 나서 정하기.** U5 실측과 N2~N5 성능 측정으로 규모를 정했다. 사용률 값이 엇갈린다는 것도 실측했기 때문에 드러났다.
- **재현 먼저, 등급은 그다음.** 저장 결함을 재현해 보니 경미 11건 중 3건이 차단 결함이었다.
- **분리 작업트리에서 측정.** 적대적 검토자가 `HAZOP-trials\adv*` 작업트리에서 패치를 따로 적용해 지적을 모두 재현했다. 마지막 점수는 3ca0bba 분리 작업트리에서 쟀다. 다른 세션의 수정에 흔들리지 않았다. 기준값 갱신 잠금(교훈 3)과 QA 규칙(교훈 2)이 이 방식을 기본으로 삼는다.

## 검토 결과 (hazop-reviewer 1회)

판정은 조건부 승인이었고 차단 2건을 고쳤다.

- 기준값 잠금이 기호 사전과 정답지를 보지 않았다. 교훈 2의 사고가 바로 기호 사전 경로였다. 두 경로를 점수 입력에 넣었고, 기호 사전 폴더는 추적 안 한 새 파일까지 본다.
- 규칙 15의 30분 한도가 규칙 7(Codex는 충분히 기다림)과 부딪혔다. 구현 세션이 아직 고치는 중일 때 총괄이 진행하면 덜 끝난 변경이 커밋될 위험도 있었다. 한도를 검토·QA 에이전트로 좁혔다.

경미 지적 중 바로 고친 것: 데스크톱 잠금 위치를 `%USERPROFILE%\.hazop\`로 옮김(Claude 앱이 `%LOCALAPPDATA%`를 가상화해 앱 안팎이 다른 파일을 봄), `desktop_lease.py run`으로 감싼 `check_user_scenarios.py`가 바깥 잠금을 물려받게 함, 옛 venv도 시험 시작 때 막음, `--pages` 확인 실행에는 디스크를 보지 않고 `HAZOP_MIN_FREE_GB`로 기준을 바꿀 수 있게 함, `check_snp_baseline.py`가 PySide6를 요구하지 않게 함, 규칙 12에 점수가 내려가는 변경의 절차를 적음, 개발 담당의 기준값 문구와 커밋 금지 문구가 어긋나던 곳, 문장 몇 곳.

후속으로 넘긴 것: 잠금 파일 경합의 드문 경우(죽은 잠금을 두 프로세스가 동시에 치울 때, 프로세스 번호 재사용), `check_apr1400.py --update`가 긴 실행 끝의 재확인에서 막히면 결과를 남기지 않는 점(`--out`을 함께 주면 남는다).
