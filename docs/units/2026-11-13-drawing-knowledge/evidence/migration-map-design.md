# 판 이전 다시 설계: 한 번 계산한 대응표를 모든 참조에 같은 함수로

- 날짜: 2026-11-18
- 대상: `feat/drawing-knowledge` @ `49033f1`(그때 푸시 안 함, `origin/feat/drawing-knowledge` = `c30c4cf`)
- 성격: 설계(2026-11-18 총괄 승인). 저장소에는 M2 구현 커밋과 함께 넣었다. 구현하며 바꾼 것은 13장, 규격은 [검토구간 규격](../../../specs/study-node-segmentation.md) §2.1·§2.6이다.
- 쓴 원칙: Attack the Premise(1장), Redesign from First Principles(2~4장), Model the Domain(2장의 자료 꼴)

## 0. 목표와 결론

**목표.** 다시 추출(앱 판 올림, 사람 다시 추출, U1 나누기·배관 고침) 뒤에 검토구간·⑤ 결과·실행 취소 기록·잠재 후보·초기사건에 저장된 참조가 **조용히 다른 기호를 가리키는 일이 없게** 한다. 못 찾는 것은 괜찮다. 다른 기호로 잇는 것은 안 된다.

**결론.**

1. 세 커밋(`cff108c`·`bd99538`·`49033f1`)의 기호 맞추기(표시 = 종류·도면·기호 종류·태그·상자 1pt)는 맞다. 퍼즈에서 표시가 있는 집합의 잘못 이음은 '표시가 같은 다른 기호'(알려진 한계)뿐이었다. 틀린 것은 **대응을 들고 다니는 방식**이다. 대응이 한 번 계산된 값으로 존재하지 않고, 필드마다 다른 함수가 자기 식으로 '잃음'을 표현한다(구간은 `lost_members`, ⑤는 `~lost` 접미사, 실행 취소 기록은 그대로, 초기사건은 손대지 않음).
2. 그래서 판 이전을 **대응표(옛 구성요소 → 새 구성요소 또는 묘비) 하나를 먼저 다 계산하고, 저장 문서를 한 번 훑는 함수 하나가 등록된 id 필드 전부에 그 표를 적용**하는 구조로 바꾼다. 등록되지 않은 자리에서 옛 id를 만나면 그 자체를 결함으로 센다(시험 실패, 실행 중에는 기록).
3. 잃은 것은 `lost:<graph_id>:<잃은 판>:<번호>` 꼴 묘비 id로 바꾼다. 살아 있는 id와 꼴이 겹칠 수 없고, 판마다 번호가 따로라 두 기호가 같은 순번으로 차례로 잃혀도 묘비가 둘이다. 되찾기는 묘비 단위다.
4. 순번 id인지는 id 꼴 정규식이 아니라 **추출 형식**으로 정한다. `build.py`가 그래프 노드에 `id_basis`(`"sequence"`·`"source"`)를 적는다. `graph_version`은 추출 결과만 해시하므로 바뀌지 않는다.
5. 본 브랜치는 세 커밋 **위에 덧쌓는다**. U1 브랜치에 같은 패치(패치 id 같음)가 들어 있어, 덧쌓으면 U1을 다시 얹을 때 세 커밋이 저절로 빠지고 U1 자기 커밋 둘만 남는다.

## 1. 전제 공격: 세 번의 고침이 함께 기댄 것

세 커밋이 모두 기댄 문장은 다음이다.

> 안정 참조 `<graph_id>#<source_object_id>`로 옛 구성요소를 새 구성요소에 잇고, 어긋나는 곳만 그 자리에서 고치면 된다(표시 확인, `lost_members`, `~lost`, 되찾기 열쇠).

이 문장은 두 갈래로 틀렸다. 지금 코드(`49033f1`)에 퍼즈를 돌려 확인했다.

**측정.** 재검토의 `fuzz_migrate.py`를 시드 0~299로 돌렸다. 판 이전 600회, 구성요소 점검 6801건, 0.66초였다(시험용 venv-py312, 2026-11-18, 저장소 밖 측정 폴더의 로그). 재검토의 시드 0~599 결과(사라짐 821~874)와 같은 꼴이다.

| 분류 | 건수(시드 0~299) | 무엇을 뜻하나 |
| --- | --- | --- |
| 사라짐(이은 구성요소가 members에도 lost에도 없음) | 412 | 장부 결함. 표가 아니라 '이름 바꾼 뒤 옛 id로 거르기'라는 차례에 기댐 |
| 잘못 이음: 표시 없는 옛 집합(참조만) | 432 | 전제 결함. 순번 id에서는 참조가 정체성이 아님 |
| 잘못 이음: 순번 id인데 상자 없음(참조만) | 42 | 같은 전제 결함 |
| ⑤ 참조가 다른 기호(1단계, 표시 없음) | 403 | 같은 전제 결함이 ⑤로 번짐 |
| 잘못 이음: 표시가 같은 다른 기호 | 66 | 알려진 한계(5.4) |
| 표시가 다른데 이음 | 0 | 기호 맞추기 자체는 맞음 |
| 예외 | 0 | |

실패의 분포를 보면 기호 맞추기 규칙에는 결함이 없다. 실패는 두 곳에 몰린다.

- **참조가 정체성이라는 가정.** 순번 id에서는 참조가 정체성이 아니다. 표시가 없으면 참조만 믿고 잇는데, 이 길에서 잘못 이음이 모두 나온다(432·42·403).
- **대응이 값으로 존재하지 않음.** 재현 넷이 모두 이 갈래다(`49033f1`에서 다시 돌려 확인, 출력은 6장).
  - 재현 1(사라짐): `migrate_set`은 `map_members`로 이름을 먼저 바꾼다. 그다음 잃은 옛 id로 거르는데, 거를 때 그 id를 이미 받은 다른 구성요소까지 지운다(migrate.py 365).
  - 재현 2(두 번 잃음): 되찾기 열쇠가 `<ref>~lost` 글자라 서로 다른 두 기호가 같은 열쇠를 갖는다(332~335).
  - 재현 4(실행 취소): `map_members`가 실행 취소 기록에 이름 바꿈만 적용하고 잃음은 적용하지 않는다(nodes.py 385~395).

즉 **어디에 어떤 id가 있는지를 아는 쪽과, 무엇이 무엇으로 바뀌었는지를 아는 쪽이 갈라져 있다.** 필드를 하나 고칠 때마다 다른 필드가 남았다. 네 번째 부분 고침은 같은 자리에서 다시 실패할 것이다.

재현 3(스캔 id)은 셋째 갈래다. '순번인가'를 id 글자 꼴로 짐작했다. 실제로는 추출 형식이 정하는 사실이다.

## 2. 처음부터 다시 짠다면: 자료 꼴

### 2.1 구성요소의 세 이름

| 이름 | 예 | 판이 바뀌면 |
| --- | --- | --- |
| `entity_id` | `entity-node-012`, `graph-X/entity-seg-003`, `xlink-…` | 늘 바뀔 수 있음(build.py 97·132의 열거 순번) |
| 안정 참조 `ref` | `graph-X#pdf-p0-sym-0012` | `id_basis == "source"`(drawio·DEXPI·`manual-`·U1 `pdf-p0-split-<op>`)면 그대로. `"sequence"`(벡터 PDF·스캔 순번)면 **다른 기호를 가리킬 수 있음** |
| 표시 `mark` | `[node_type, sheet, kind, tag, x0, y0, x1, y1]` | 같은 기호면 그대로(1pt 안) |

정체성 규칙은 하나다. `source` 구성요소는 `ref`가 정체성이다. `sequence` 구성요소는 `mark`가 정체성이고 `ref`는 동률일 때만 쓴다.

### 2.2 판 사진(snapshot): 집합이 가리키는 판의 정체성

집합 문서에 지금처럼 그래프 전체 정체성을 둔다. 필드 이름은 읽는 곳이 많아(`ie/model.py` 165, `convert.py` 94 등) 그대로 둔다. 쓰는 곳은 함수 하나로 모은다.

```text
graph_member_refs  {entity_id: ref | null}     # 그대로
graph_member_marks {entity_id: mark}           # 그대로. 단 id_basis == "sequence"이고 상자가 있는 것 전부(스캔 포함)
graph_member_basis {entity_id: "sequence"|"source"}   # 새로. 없으면(옛 집합) 4.1의 대체 규칙
```

`snapshot(graph) -> {"graph_member_refs", "graph_member_marks", "graph_member_basis"}`를 `new_set`·`with_refs`·`confirm_nodes`·판 이전 끝이 똑같이 부른다. 지금은 두 줄짜리 갱신이 네 곳에 흩어져 있다.

### 2.3 묘비(tombstone)

```text
tombstones: {
  "lost:graph-X:v-1a2b3c4d5e6f:3": {
    "entity_id": "entity-node-012",      # 잃기 직전 판의 id(기록용, 다시 쓰지 않음)
    "ref": "graph-X#pdf-p0-sym-0012",    # 잃기 직전 판의 참조(기록용)
    "mark": [...] | null,                # null이면 되찾지 않음
    "basis": "sequence" | "source" | null,
    "lost_from": "v-…(옛 판)", "lost_at": "v-…(새 판)", "at": "2026-…",
    "legacy_key": "graph-X#pdf-p0-sym-0012~lost" | null,   # B꼴에서 옮긴 것만(5.2)
    "found": null | {"entity_id", "ref", "version", "at"}
  }
}
```

- **묘비 id는 `lost:<graph_id>:<lost_at 판>:t-<지문>`다.** 지문은 graph_id·잃기 전 판·잃은 판·옛 entity_id·옛 참조·표시의 sha256 앞 12자다(13.3에서 고침. 처음 설계의 '그 판 이전에서 잃은 것의 차례'는 같은 판으로 두 번 오면 겹쳤고, 13.2의 집합 일련번호는 집합을 새로 제안하거나 백업에서 되돌리면 겹쳤다).
  - 살아 있는 id와 겹치지 않는다. `entity_id`는 `entity-`·`relation-`·`xlink-`·`<graph_id>/`로 시작하고, `ref`는 `graph-`·`project-`로 시작한다. `lost:`로 시작하는 것은 없다. 이 사실은 시험으로 지킨다(7.3).
  - 결정적이다. 같은 입력이면 같은 id라서 두 번 적용해도 같다. 같은 id면 같은 잃은 기호다(판 문자열이 내용 해시라 잃기 전 판과 옛 entity_id가 기호 하나를 정한다).
  - 판이 id에 들어 있어, 같은 순번 참조가 다른 판에서 두 번 잃혀도 묘비가 둘이다(재현 2가 구조로 막힘).
  - `graph_id`가 들어 있어, 프로젝트 단위 초기사건 문서에서 다른 도면 묘비와 섞이지 않는다.
- 묘비는 지우지 않는다. 되찾아도 `found`만 채운다. 구간을 지워도 묘비 기록은 남는다(지금 `remove_empty`가 잃은 기록을 이력 없이 지우는 것을 막음).
- 구간 쪽 잃은 구성요소는 `nodes[].lost: [묘비 id]`로 둔다. `members`에는 늘 지금 판의 살아 있는 id만 있다. 이 규칙 덕에 `members`를 읽는 많은 곳(분할·지문·화면 강조)은 고치지 않는다.

### 2.4 대응표

```text
Table = {
  "graph_id", "from": 옛 판, "to": 새 판,
  "eid":   {옛 entity_id: 새 entity_id | 묘비 id},   # 옛 판 사진의 모든 구성요소 + 문서에서 만난 떠돌이 id. 전함수
  "ref":   {옛 ref: 새 ref | 묘비 id},               # eid에서 판 사진으로 유도. 이 graph_id의 참조만
  "found": {묘비 id: [새 entity_id, 새 ref]},        # 앞서 만든 묘비를 이번에 되찾은 것
  "new_tombs": {묘비 id: 기록},
  "check": "mark" | "content" | "ref",              # 순번 구성요소를 무엇으로 확인했나(4.1)
  "partial": bool                                    # 이력에서 복원한 표(바뀐 것만 담음)면 참
}
```

- `eid`는 **전함수**다. 옛 판의 모든 구성요소가 새 구성요소 하나나 묘비 하나로 간다. '그대로 두는' 값은 없다.
- **전단사 검사.** 옛 구성요소 둘이 한 새 구성요소로 모이면 둘 다 묘비가 된다(지금 299~304의 규칙을 표 계산 안으로 옮김). 되찾기도 같은 검사를 받는다. 이미 이어진 새 구성요소는 되찾을 수 없고, 묘비 둘이 한 새 구성요소를 다투면 둘 다 못 찾는다.
- 이력(`history[].detail`)에는 바뀐 것만 남긴다.
  - `renamed {옛 eid: 새 eid}`(이름 유지: U1 R2 시험이 읽음)
  - `lost {옛 eid: 묘비 id}`, `ref_moved {옛 ref: 새 ref | 묘비 id}`, `found {묘비 id: 새 eid}`
  - `check`, `unregistered`(7.2), `recheck`, `demoted`
  - 결과 파일이 늦게 따라올 때 이 기록으로 `partial` 표를 만든다(3.3).

### 2.5 id를 담는 필드 목록(등록부)

한 곳(`hazop/study/idmap.py`의 `FIELDS`)에 문서 종류별로 경로와 공간을 적는다. 경로 문법은 `a.b[].c`이고, `[]`는 목록의 모든 항목이다.

| 문서 | 경로 | 공간 |
| --- | --- | --- |
| 검토구간 집합 | `nodes[]` · `nodes[].absorbed[]` · `nodes[].parts[]` | `MEMBERS`(아래) |
| | `batches[].ops[].before` · `.after` 및 그 `absorbed[]`·`parts[]` | `MEMBERS` |
| | `previous[].nodes[]` · `legacy.previous[].nodes[]` · `legacy.excluded_nodes[]`(+`absorbed[]`·`parts[]`) | `MEMBERS` |
| | `nodes[].boundary_hint.from` · `.to` | `EID` |
| ⑤ 결과 | `cells[].entries[].cause_refs[].ref` · `consequence_refs[].ref` · `safeguards[].refs[].ref` | `REF` |
| | `cells[].entries[].expectation_refs[]` | `EXP` |
| | `cells[].entries[].ai_basis.kg_paths[][]` | `EID`(이 표의 옛 도메인에 있는 것만. knowledge id는 지나감) |
| | `archived_cells[].cell.entries[]…` 위 전부 · `cells[].entries[].history[].before.*` 위 참조 필드 | 같음 |
| 초기사건(U3) | `basic_events.*.ref` · `basic_events.*.key`(`ref|mode`) · `headings[].targets[]` | `REF` · `BEKEY` · `REF` |
| FMEA(U3) | `rows[].ref` · `rows[].entity_id` | `REF` · `EID` |
| 잠재 후보 판단(U3) | `judgements` 열쇠(`rule|ref`) · `.target` · `.found[]` · `.rejected[]` | `JKEY` · `REF` |

일부러 옮기지 않는 자리(`IGNORED`)도 같은 파일에 적는다.

- `history[]`: 지난 일의 기록이라 옛 판 id가 맞다.
- `graph_member_refs`·`graph_member_marks`·`graph_member_basis`·`member_digest`: 판 이전 끝에 새 그래프로 다시 만든다.
- `tombstones`: 기록이다.
- 구간 AI 검토 파일(`node_review.py`): 옮기지 않는다. 처음 설계는 '`input_fp`로 이미 오래됨 처리가 된다'고 보았으나 틀렸다. 다시 추출로 구간 안 순번이 맞바뀌면 구간 구성요소 목록이 같아 `input_fp`가 그대로이고, 받아 둔 제안의 `split_off`가 다른 기호를 떼어 낸다(13.2 차단 5). 그래서 제안에 받은 판(`graph_version`)을 적고 판이 바뀌면 오래됨으로 한다. 제안은 다시 받을 수 있으니 옮기는 것보다 단순하다.
- 분석 실행 폴더 `analysis.json`: 불변 기록이다.

`MEMBERS` 공간은 `members`를 가진 사전 하나에 거는 규칙이다.

1. `members`의 각 id를 번역한다.
2. 묘비가 된 것은 `lost`로 옮긴다.
3. `lost`의 묘비 가운데 이번에 되찾은 것은 `members`로 돌린다.

구간, 실행 취소 기록의 before/after, 조각, 옛 판 사진에 모두 같은 규칙이다. 그래서 되돌려도 묘비는 묘비로 남는다(재현 4가 구조로 막힘).

### 2.6 공간별 번역 함수

```python
def translate(x, space, table, rules_cache) -> x2
```

- 묘비 id이고 `table.found`에 있으면 새 id(공간에 맞게 eid 또는 ref)로 바꾼다. 아니면 그대로 둔다.
- `EID`: `table.eid[x]`. 표에 없는 살아 있는 꼴 id는 1차 훑기에서 떠돌이로 모아 표에 묘비로 넣어 둔다(아래 3.2).
- `REF`: `drawing_of(x)`가 이 표의 `graph_id`(프로젝트 그래프면 그 시트들)가 아니면 그대로 둔다. 다른 도면 참조는 그 도면의 판 이전이 맡는다. 같은 도면이면 `table.ref[x]`이고, 옛 판 사진에 없는 참조는 묘비다.
- `EXP`: `exp-<rule>-<hash(ref)>`.
  - 규칙마다 `{expectation_id(rule, r): r}`를 한 번 만들어 거꾸로 찾는다. 지금 `_move_expectations`는 항목마다 `forward` 전체를 훑는다.
  - 대상이 묘비면 `<묘비 id>|exp:<rule>`로 바꾼다. 되찾으면 `expectation_id(rule, 새 ref)`로 돌린다. 해시 충돌에 기대지 않는다.
- `BEKEY`(`ref|mode`)·`JKEY`(`rule|ref`): 안의 `ref`만 `REF` 규칙으로 바꾼다.

- 판이 같으면 3 이후를 하지 않는다. 같은 표를 두 번 계산하면 같은 묘비 id가 나온다(결정적). 따라서 '두 번 적용해도 같음'(불변식 ④)은 구조로 선다.

## 4. 순번 id 판단: 추출의 사실로

### 4.1 `id_basis`를 어디서

조사 결과(이 설계 때 읽음, 하위 에이전트 보고를 원문으로 대조):

- `graph_version`은 `BUILDER_VERSION + 추출 결과 전체`의 해시다(build.py 75~78). 제외 목록은 없다.
  - **추출 결과에 필드를 더하면 모든 판이 바뀐다.** 기준값과 X2 검사가 깨진다.
  - **그래프 노드에만 필드를 더하면 판은 그대로다.** 값이 추출 결과에서만 유도되기 때문이다.
- 그래프에는 추출 형식(`source.format`)이 없다. `sources.py` 54~63은 추출 파일을 다시 열어 형식을 읽는다.
- 형식별 id(인용은 보고 원문, 대표 몇 줄은 직접 대조):

  | 형식 | id | 판단 |
  | --- | --- | --- |
  | 벡터 PDF | `pdf-p%d-sym/junction/conn/text-%04d`(pdf_vector.py 3791·3924·3970·4056·4103) | 순번 |
  | 스캔 | 같은 함수를 부른 뒤 `raster._retag`가 `pdf-p0-`를 `img-`로 바꿈(raster.py 1441~1452) | 순번 |
  | drawio | mxCell id | 고정. id 글자는 아무 꼴이나 될 수 있다. **그래서 글자 꼴로는 판단할 수 없다** |
  | DEXPI | 파일에 적힌 개체 id | 고정. 단 가져오기가 지은 id(Proteus Connection `<구간>__Connection_<n>`, 쪼갠 조각, ID 없는 부품의 경로 id)는 순번(M1 `8677846`에서 바로잡음) |
  | 사람이 더함 | `manual-<op_id>`(corrections.py 22) | 고정 |
  | U1 나누기 | `pdf-p0-split-<op_id>` | 고정(연산에 묶인 이름) |

**정함.** 형식에서 정하고 노드에 적는다.

1. `hazop/extract/ids.py`(새, 추출 쪽 소유)
   - `basis(fmt, soid) -> "sequence" | "source"`를 둔다.
   - `fmt in {"pdf_vector", "raster_png", "raster_jpeg"}`이고 `soid`가 `manual-`·`pdf-p<n>-split-`로 시작하지 않으면 `"sequence"`, 아니면 `"source"`다.
   - 머리 문자열 `MANUAL_PREFIX`·`SPLIT_PREFIX`는 `corrections.py`·`pdf_vector.py`가 쓰는 값과 같은 상수를 가져온다.
2. `build.py`: 노드·구간(`entity-seg`) 사전에 `"id_basis": ids.basis(형식, soid, 지은 id인가)`를 넣는다. 추출 결과에서 유도되므로 `graph_version`은 그대로다. (M1 정정: 그래프 머리 `source`에는 `format`을 넣지 않았다.)
3. 프로젝트 그래프: 시트 노드는 그 시트 그래프의 `id_basis`를 가져오고, 없는 옛 시트는 그 시트의 추출 파일에서 읽어 복사본에 적는다. 도면 연결(xlink) 구간은 id가 두 끝의 `source_object_id` 해시이므로 두 끝이 모두 `source`일 때만 `source`다.
4. **대체 규칙**(`id_basis`가 없는 옛 `graph.json`)
   - 그래프 머리 `source.extraction_file`이 가리키는 추출 파일의 형식을 읽는다.
   - 형식을 모르면 `sequence`(위치로 다시 확인하는 안전한 쪽). M1에서 글자 꼴 짐작은 없앴다.
5. 시험(`tests/test_extract_ids.py`). **어댑터가 실제로 낸 id 전부**를 분류해 본다.
   - 작은 벡터 PDF 고정 자료와 스캔 고정 자료를 실제로 추출한다. 모든 `source_object_id`가 `"sequence"`여야 한다.
   - drawio·DEXPI 고정 자료는 모두 `"source"`, `manual-`·`split-`도 `"source"`여야 한다.
   - `build_graph`가 낸 모든 노드에 `id_basis`가 있어야 한다.
   - `graph_version`이 필드를 넣기 전과 같아야 한다. 같은 추출 결과로 앞뒤 코드를 비교한다.

**버린 안.** 추출 결과에 `id_stable`을 적는 안이다. 모든 `graph_version`이 바뀌고 기준값을 다시 매겨야 한다. 이 일에 비해 값이 크다.

### 4.2 순번 구성요소를 무엇으로 확인하나(`check`)

| 옛 사진 | 순번 구성요소의 잇기 | `check` |
| --- | --- | --- |
| 표시 있음 | 표시가 맞는 것 하나(동률이면 같은 ref) | `mark` |
| 표시 없음(A꼴, 또는 B꼴의 스캔·상자 없는 것) | 그 구성요소가 든 구간 가운데 **기록한 md3가 참조 잇기로 다시 센 md3와 같은 구간**이 하나라도 있으면 참조로 잇는다. 아니면 묘비 | `content` |
| 상자 없는 순번 구성요소 | 묘비 | `mark` |

`content`가 맞는 이유가 있다. md3는 구성요소마다 `ref`·종류·태그·배관 번호·흐름·정상/고장 위치와 닿는 관계를 담는다. 참조 잇기로 다시 센 값이 같으면, 각 참조가 종류·태그·연결이 같은 구성요소를 가리킨다. 그러니 다른 기호로 이었다 해도 내용으로는 구별할 수 없는 기호끼리다(5.4 한계와 같은 종류). md3가 없는 적용됨 구간의 구성요소와 구간 밖 구성요소(⑤ 영향 대상 등)는 표시 없이 확인할 길이 없으므로 묘비다.

이 규칙은 퍼즈의 '표시 없는 옛 집합' 잘못 이음(432·403)을 0으로 만들 것으로 예상한다. 대신 묘비가 는다. 실제 크기는 U2 QA에서 134쪽 replay로 잰다(아직 재지 않음).

## 5. 이미 저장된 옛 꼴 읽기

`idmap.upgrade`가 한 번만 옮긴다. 옮긴 문서에 `id_scheme: 2`를 적고, 2이면 다시 보지 않는다. 쓰기는 지금 `on_load`의 '백업 → `write_json(expect=fp)`'를 그대로 탄다. 결과 파일도 같다.

### 5.1 A꼴(`cff108c` 이전: 표시 없음, `lost_members` 없음, `~lost` 없음)

- 판이 같으면 사진(표시·basis)을 채우고 `id_scheme: 2`를 적는다. 그 뒤로는 표시로 확인한다.
- 판이 다르면 4.2의 `content` 규칙으로 판 이전을 한다.

### 5.2 B꼴(`cff108c`~`49033f1`: `graph_member_marks`, `nodes[].lost_members`, `~lost`)

1. `nodes[].lost_members[]`의 각 기록을 묘비로 바꾼다.
   - id는 `lost:<graph_id>:<기록의 from 다음 판, 모르면 'legacy'>:<번호>`다. `ref`·`mark`·`from`을 옮기고 `legacy_key = ref + "~lost"`로 둔다. 이 묘비 id를 `nodes[].lost`에 넣는다.
   - `entity_id`가 None이거나 기록이 사전이 아니면 묘비를 만들지 않고 보고에 센다. 퍼즈의 손상 기록(`[None]`·`["x"]`·`[{}]`)이 여기 걸린다.
2. ⑤·초기사건의 `X~lost`
   - 같은 `legacy_key`를 가진 묘비가 **하나**면 그 묘비 id로 바꾼다.
   - **둘 이상**(재현 2로 생긴 것)이면 그 모두를 '되찾지 않음'(`mark: null`)으로 낮춘다. 그 참조는 새 묘비 `lost:<gid>:legacy:r-<sha8(X)>`로 바꾼다.
   - **없으면**(구간 밖 대상) 같은 꼴의 되찾지 않는 묘비로 바꾼다.
3. `exp-…~lost`: 묘비들의 `ref`로 해시를 거꾸로 찾아 `<묘비 id>|exp:<rule>`로 바꾼다. 못 찾으면 되찾지 않는 묘비로 바꾼다.
4. `kg_paths`의 `entity-…~lost`: `entity_id`가 같은 묘비가 하나면 그것으로, 아니면 되찾지 않는 묘비로 바꾼다.
5. 이력의 B꼴 `migrate_version` 줄(`unmapped`, `ref_moved`의 None 값, `<ref>~lost` 열쇠)
   - `from_record`가 읽을 수 있게 둔다. None은 '이 줄에서 잃음'으로 읽는다.
   - 묘비 id는 `lost:<gid>:<그 줄의 to>:r-<sha8(옛 ref)>`로 결정적으로 만든다. 그래서 늦게 따라오는 결과 파일도 같은 id를 받는다.
6. `graph_member_marks`는 그대로 쓴다. 단 B꼴은 정규식에 걸린 것에만 표시가 있다. 스캔(`img-`)·상자 없는 순번 구성요소는 표시 없음이므로 4.2의 `content` 규칙을 탄다.

### 5.3 깨진 저장본

- `_check_shape`가 `tombstones`(사전, 열쇠는 `lost:`로 시작), `nodes[].lost`(문자열 목록), `graph_member_marks`의 값 모양, B꼴 `lost_members`(목록)를 본다.
- 어긋나면 지금처럼 `ValueError`로 읽지 않는다. 지금은 표시·`lost_members`의 모양을 보지 않아 `TypeError`로 멈춘다(재검토 재현).

### 5.4 그대로 두는 한계(규격에 적음)

**태그가 없는 같은 종류 기호가 같은 상자(1pt 안)에 있으면 같은 기호로 본다.** 다시 추출 사이에 겹친 두 기호가 자리를 바꾸면 구별할 수 없다. 퍼즈에서 '표시가 같은 다른 기호' 66건(시드 0~299)이 이 경우다. 규격 §2.6에 '알려진 한계'로 적고, 퍼즈는 이 분류를 따로 세어 실패로 치지 않는다.

### 7.2 등록부가 새 필드를 놓치지 않게

**실행 중 감지.** `apply`는 문서 **전체**를 훑는다. 등록된 경로에서는 번역한다. 등록되지 않았고 `IGNORED`도 아닌 자리에서 문자열 잎이 이 표의 옛 도메인(`table.eid` 열쇠 ∪ `table.ref` 열쇠 ∪ 그 잠재 후보 ID)에 들면 `report["unregistered"]`에 경로를 적는다.

- 시험에서는 이것이 비어 있어야 한다.
- 앱에서는 이력 줄의 `unregistered`에 남기고, 화면의 '참조 확인 필요'를 켠다.
- 누가 새 필드에 id를 저장하기 시작하면, 그 문서가 처음 판 이전을 거칠 때 드러난다.

**시험 고정 자료.** `tests/test_study_idmap_fields.py`는 공개 쓰기 함수로 '모든 필드가 찬' 문서를 만든다.

- 검토구간: `propose → split → merge → remove_member → edit → undo → confirm → lock`, AI 검토 수락, 0.1 변환본
- ⑤: 원인·영향·보호수단·잠재 후보·근거 경로·편집 이력·보관 칸
- 초기사건·FMEA·잠재 후보 판단: U3

그 문서를 판 이전에 넣어 `unregistered == []`이고, 등록부의 모든 경로가 적어도 한 번 값을 만났는지 확인한다. 죽은 등록 항목도 실패로 잡는다.

## 8. 남은 위험

1. **5.4 한계.** 태그 없는 같은 종류가 같은 상자면 같은 기호로 본다.
2. **등록부는 '문서에 값이 있을 때'만 새 필드를 잡는다.** 쓰기 함수가 생겼는데 고정 자료가 그 길을 안 타면 시험은 못 잡는다. 실행 중 감지(7.2)가 첫 판 이전에서 잡는다. 그 전까지의 틈은 남는다.
3. **A꼴 집합의 첫 판 이전에서 묘비가 많이 생길 수 있다.** 놓치는 쪽으로 기운 결정이다. md3가 없는 적용됨 구간과 구간 밖 ⑤ 영향 대상이 묘비가 된다. 크기는 U2 QA의 134쪽 replay로 재서 보고한다(아직 모름).
4. **늦게 따라오는 문서.** 이력의 `partial` 표로 옮기므로 떠돌이 검출이 없다. 결과 파일 쓰기가 실패한 드문 경우다.
5. **초기사건 확정 그룹이 내려감.** ⑤ 참조를 옮기면(같은 기호의 새 이름이어도) 초기사건 승인 지문이 바뀐다(`ie/model.py` 192·340~350). 지금도 같다. 규격 §5.3 '참조 ID의 판 이전은 내용 변경이 아니다'와 어긋나므로, U3에서 지문을 '번역된 참조' 기준으로 셀지 정한다.
6. **옛 앱이 새 파일을 읽으면 묘비 id를 날것으로 보인다.** 덮어쓰지는 않는다(모르는 필드를 깊은 복사로 보존함). 집합 `schema_version`은 올리지 않고 `id_scheme: 2`로 둔다. 올리면 막을 수 있지만 `_usable`·변환·시험 수십 곳이 흔들린다. 사용자 승인 대기로 적을 일은 아니고, 권장안으로 정한 것으로 남긴다.
7. **프로젝트 그래프 집합.** 노드 id가 `<graph_id>/entity-…`이고 참조의 도면이 시트마다 다르다. `REF` 번역의 '이 표의 도면'은 프로젝트 그래프의 시트 집합으로 정한다. 프로젝트 판(`pv-`)이 시트 판을 묶는 방식(project.py 503)대로 시트 하나만 다시 추출돼도 표 하나로 처리되는지 U2에서 시험한다.
8. **`links.csv`(지식 입력)는 사람이 쓴 입력이라 고쳐 쓰지 않는다.** 행마다 `graph_version`·`target_source_object_id`가 있어 `kg.link`의 재확인이 이미 판 차이를 본다. 판 이전 표를 '제안'으로 보여 주는 일은 뒤 단위다.

## 14. M3: ⑥ 초기사건 문서·FMEA·잠재 후보 판단(2026-11-23)

9장의 갈고리를 넣었다. 재현(`fixflow/migrate2/m3/test_m3_repro.py`)을 `tests/test_ie_refs_migrate.py`로 옮겨 612de7f에서 네 시험이 실패하는 것(표제 대상·기본사건·FMEA·묶음 표제가 다른 기호, 대조군만 통과)을 먼저 보였다.

**등록부.** 경로에 `{}`(ID를 열쇠로 쓰는 사전의 값)를 더했고, `{}`로 끝나는 경로는 그 사전의 열쇠를 옮긴다(잠재 후보 판단 `judgements{}`). 공간은 둘을 더했다. `head`는 `<참조>|<나머지>`(기본사건 열쇠), `tail`은 `<규칙>|<참조>`(판단 열쇠)다. 옮긴 열쇠가 앞 항목과 겹치면 뒤 항목은 옛 열쇠의 지문으로 지은 묘비 열쇠(`k-`)로 두어 덮지 않는다. 미등록 감지는 `{}` 아래를 열쇠 대신 `{}`로 맞춰 그대로 돈다. 세 문서의 자리는 규격 HZ-PLN-17 §8.3 표와 같다. 9장 표에 적었던 FMEA `history[].before.entity_id`는 실제로 생기지 않아(행 고침 이력은 CONTENT만 적음) 넣지 않았다(등록 항목이 실제 문서에 나오는지 보는 시험이 잡음).

**판 표지.** 9장의 `ref_versions: {graph_id: graph_version}`과 '⑤ 결과의 판을 표지로 쓴다'는 추정은 버렸다. 판 문자열만으로는 A→B→A를 가리지 못하고, ⑤ 결과의 판은 ⑥ 문서가 마지막으로 옮겨진 판을 말해 주지 않는다. M2 결과와 같이 집합 이력의 판 이전 줄 번호(`step`)를 표지에 함께 적고 그 뒤 줄만 적용한다(`hazop.study.follow.plan`). 줄이 지금 판까지 이어지지 않으면 옮기지 않고 그 집합 도면의 참조를 모두 묘비로 한다.

표지 없는 문서는 문서 시각으로 미루어 본다. 문서의 모든 시각이 두 판 이전 줄 사이에 들고, 집합 이력의 첫 시각이 문서의 첫 시각보다 늦지 않을 때만 그 사이 판에서 쓴 것으로 본다. 끼면(MIXED), 시각 없는 기록이 있으면(NO_TIME), 집합이 문서보다 늦게 생겼으면(YOUNGER, 구간을 새로 제안), 옮긴 기록은 있는데 표지가 없으면 묘비다. 마지막 시각만 보는 안(총괄 메모)은 쓰지 않았다. M3 전 문서는 판 이전을 받은 적이 없어, 마지막 시각이 판 이전 뒤여도 참조는 그 전에 쓴 것일 수 있다(퍼즈가 잡음).

**도면 연결 구간.** `xlink-…` 참조는 도면 접두가 없고 id가 양 끝 참조의 해시라, 증명하지 못한 문서에서 남겨 두면 다른 판의 같은 id가 다른 기호 쌍을 가리킨다(퍼즈 시드 3·90). 프로젝트 그래프 집합이면 `xlink-` 참조와 id를 모두 그 집합의 것으로 보고 함께 묘비로 한다.

**차례.** `migrate.on_load`가 ⑤ 결과 다음에 세 파일을 백업하고 읽은 지문으로 원자적으로 쓴다(`follow.write_after`). 쓰지 못한 파일은 읽는 쪽(`ie.store.load`·`load_fmea`, `expect.load_judgements`)이 디스크의 집합 이력으로 메모리에서 이어 옮긴다(`follow.catch_up`). 프로젝트 전체 집합이 있으면 그것만 따른다. 같은 도면을 두 집합이 옮기면 두 번 적용되기 때문이다. `save_judgement`는 표지를 지우지 않게 고쳤다.

**묶음과 확정.** 묘비 기본사건의 태그 사본은 '확인 필요 (이전 태그 …)'로, 참조는 '대상 없음(…확인 필요)'으로 낸다. 지금 도면에 없는 참조도 날것으로 내지 않는다. 그룹 지문이 바뀌면 초안으로 내려가는 동작은 두고, 묘비가 남은 그룹은 확정을 막았다(`model.lost_problems`, 확정 문제에 듦). 경고만 하는 안은 사람이 ⑤를 다시 승인하고 그룹을 다시 확정하면 대상을 모르는 표제가 '확정'으로 나가는 길(재현 out_synth: drop 시나리오 네 그룹 모두 다시 확정됨)을 열어 두므로 고르지 않았다. 대상이 묘비가 된 승인 FMEA 행은 가져옴으로 되돌리고 묘비 행은 승인하지 못한다.

**시험.** `tests.test_ie_refs_migrate`(11개: 재현 5, 묶음 '확인 필요', 다시 확정 막기, FMEA 되돌림, 다시 열어도 파일 그대로, 표지 없는 문서를 판 이전 사이에 고침, 등록 항목이 모두 실제 문서에 나오고 미등록 자리 없음), `tests.test_study_migrate_chain.ProjectDocChainTest`(5개: A→B→A, 늦게 따라옴 = 즉시, 잘린 이력·되돌린 집합, 새로 제안한 집합의 표지 없는 문서, 판단 열쇠), 퍼즈에 세 문서(따라감·건너뜀·되돌아온 판에서 새로 단 표제 대상·사슬 끝의 표지 없는 옛 문서와 가운데 고친 옛 문서)를 넣었다. 판정은 생성기의 진짜 정체다. 고친 곳을 하나씩 되돌린 변이 다섯(확정 막기, 묶음 표시, FMEA 되돌림, 표지 무시, 따라가기 끔)은 모두 해당 시험이 잡았다.

## 15. 찾지 못한 구성요소 버리기(2026-11-23)

**문제.** 판 이전이 찾지 못한 구성요소는 구간의 `nodes[].lost` 묘비로 남는다. 사람이 대신할 구성요소를 구간에 다시 골라도 묘비는 스스로 닫히지 않았고, 닫는 명령도 없어 '찾지 못한 구성요소 n개'가 줄지 않았다(s-viewer 확인). 재현은 `tests.test_study_discard_lost`의 `test_repicking_the_redrawn_component_leaves_the_lost_count_until_it_is_discarded`다. V1을 지우고 V1B를 새로 그린 도면에서 V1B를 S1에 다시 골라도 `lost_members`가 `{"S1": 1}`이고, 6ec8d53에서는 `nodes.discard_lost`가 없어 실패한다(같은 파일의 시험 11개가 모두 실패했다. 9개는 함수·명령이 없어서(AttributeError, unknown_command)이고 2개는 시험 자료 잘못(묘비 수, 빈 칸 목록)이라 시험을 고쳤다).

**다시 고르면 저절로 닫는 안을 버린 까닭.** 사람이 고른 새 구성요소가 어느 묘비를 대신하는지 엔진은 모른다. 종류·태그가 같아도 다른 자리일 수 있고(2.4의 알려진 한계와 같은 꼴), 하나를 고르며 묘비 둘을 닫으면 다른 쪽을 조용히 잃는다. 그래서 사람이 묘비를 골라 버리는 명령을 따로 둔다.

**자료 꼴.** 버린 묘비는 `lost`에서 같은 구간의 `discarded`로 옮긴다. 묘비 기록(`tombstones`)에는 표시를 달지 않는다. 구간에 두면 실행 취소 기록(`batches[].ops[].before·after`)이 그대로 담아 되돌리기가 공짜로 되고, 묘비 기록에 달면 되돌리기가 구간만 되살리고 표시는 남는 어긋남이 생긴다. 버린 상태는 지금 구간에서 셈한다(`idmap.discarded_tombs`: 어느 구간의 `discarded`에 있고 어느 구간의 `lost`에도 없는 묘비). `discarded`에는 묘비 id만 두므로 등록부·미등록 감지에 새 자리가 필요 없다(옛 id나 참조를 사본으로 두면 `_unregistered`가 잡는다). 누가·언제·무엇은 이력 `discard_lost` 줄에 둔다.

**판단.**

| 물음 | 고른 것 | 근거 |
| --- | --- | --- |
| ⑤·⑥·FMEA·잠재 후보의 같은 묘비 참조 | 지우지 않음. `lost_refs`에 계속 세고 `discarded_refs`로 따로 알림, 표시는 `label(…, discarded=…)` | 항목 문장은 사람이 썼다. 구간에서 구성요소를 버린 것이 원인·영향 문장을 무효로 만들지 않는다. 자동으로 지우면 ⑥ 그룹 확정 막기(14장)도 풀려 대상 없는 표제가 나간다 |
| 되찾기 | 버린 묘비는 되찾지 않음 | 사람이 이미 다른 구성요소를 골랐을 수 있어, 되찾으면 같은 기호가 두 번 들 수 있다. 겹친 다른 구간에 열린 채 남은 묘비는 되찾는다 |
| 되돌리기 | 묶음 하나, `undo_batch`로 되살림 | 다른 편집과 같은 길 |
| 확정·잠금 구간 | 거절(확정 해제 뒤) | 확정 중 허용하면 묶음 `after`와 확정 해제 뒤 구간이 달라 되돌리기가 막힌다. 판 이전이 잃은 확정 구간은 적용됨으로 내리므로 보통은 문제가 없다. 사람이 잃은 것을 둔 채 확정한 구간만 한 번 해제해야 한다. `rev`·구간 지문은 그대로라 다시 확정하면 같은 판이다 |
| 채팅 | AI 동작으로 열지 않음 | 사람이 확인했다는 기록이다 |
| 같은 버리기 두 번 | 받은 집합 그대로 | 이미 버린 것·남은 것 없음은 할 일이 없음. 이 구간에 없던 묘비는 `ValueError` |

**퍼즈.** `tests.test_study_discard_fuzz`가 판 이전 퍼즈(`run`에 갈고리 `after_step` 하나를 더함)에 버리기를 섞는다. 판 이전마다 적용됨 구간의 묘비 하나·여럿·전부를 퍼즈 난수와 따로 버리고, 퍼즈의 ①~⑧에 더해 ⑨ 버린 묘비를 되찾지 않음, ⑩ 버린 뒤 세는 수, ⑪ 두 번 버리기를 본다. ①은 `discarded`의 묘비도 '사람이 버림'으로 세어 사라짐이 아니다(`check_holder` 한 줄). 되찾기 제외를 지운 변이는 ⑨가 잡았다(300시드에서 32건).
