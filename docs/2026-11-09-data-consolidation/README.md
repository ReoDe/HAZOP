# `데이터/`·`참고자료/` 정리 설계 (①단계: 조사·구조 설계)

작성 2026-11-09. 이 문서는 설계만 담는다. 파일 이동과 코드 수정은 사용자 결정(②) 뒤 ③단계 세션이 한다.

목표는 저장소의 `데이터/`와 루트 `참고자료/`를 한 체계로 정리하는 것이다. 지금 코드와 사용자 데이터가 계속 맞아야 하고, 새 기능이 폴더를 더할 때 규칙이 하나여야 한다. 무엇보다 사람이 한 작업 결과를 잃지 않아야 한다.

## 0. 다시 만드는 법

```bash
python scripts/inventory_data_paths.py
```

`inventory/` 아래 세 파일이 다시 생긴다. 같은 저장소 상태에서는 결과가 같다. ③단계 세션은 이전 전후에 한 번씩 돌려 비교한다.

- `inventory/references.csv`: 참조 한 건마다 파일·행·원본 종류·루트·하위 폴더·대상 분류·접근 방식·행 내용
- `inventory/folders.csv`: 하위 폴더마다 git 추적·미추적·ignore 파일 수, 크기, 배포본 묶음 여부, 분류, 참조 수
- `inventory/summary.md`: 두 표의 요약

훑는 범위는 git 추적 파일과 미추적 파일(ignore 제외), 그리고 `데이터/`·`참고자료/` 아래 ignore 파일이다. 확장자는 `.py .md .json .csv .spec .ps1 .txt .html` 등 글자 파일만 보고, `licenses/`와 `.claude/worktrees/`는 뺀다. PyInstaller spec은 저장소에 없고 `scripts/build_package.py`가 그때그때 만든다. 그래서 묶음 대상은 그 파일의 `DATA_DIRS`·`DATA_FILES`를 AST로 읽어 정한다.

'데이터'는 일반 낱말이기도 하다. 그래서 뒤에 `/`·`\`가 붙었거나 따옴표·백틱으로 감싼 경우만 경로 참조로 센다. 이 규칙 때문에 `"데이터 파일을 읽는다"` 같은 문장은 빠지고, 경로가 문장 안에 따옴표 없이 홀로 나오면 놓칠 수 있다.

### 목록에서 드러난 점

1. **경로 문자열이 사용자 데이터 안에 저장된다.** 구간 JSON의 `inputs`가 자원 루트 기준 상대 경로를 들고 있다(`데이터/구간/region-SNP-M-102-pzr.json:181-184`의 `"데이터/이탈후보/..."` 등). 배포본 사용자의 `%LOCALAPPDATA%\HAZOP\데이터\구간\*.json`에도 같은 문자열이 들어 있다. 자원 폴더를 옮기면 옛 문자열을 새 위치로 풀어 주는 별칭이 없으면 분석이 "파일 없음"으로 멈춘다.
2. **추출 결과도 경로로 출처를 판단한다.** `hazop/app/data.py:214`는 추출 JSON의 `source.file`이 `"참고자료/"`로 시작하면 "샘플 실행 데이터"로 표시한다. `출력/` 아래 18개 파일이 이 문자열을 갖고 있다. 참고자료를 옮기면 옛 결과와 새 결과 모두를 알아보게 바꿔야 한다.
3. **도면 그래프의 판(`graph_version`)이 경로 문자열에 묶여 있다.** `hazop/graph/build.py:75-78`은 추출 JSON 전체를 해시해 판을 만든다. 그 안의 `source.file`은 작업 루트 기준 상대 경로다(`hazop/extract/drawio.py:861`, `scripts/extract_drawio.py:58`). 검토자가 `출력/추출/SNP-M-102/extraction.json`의 `source.file`만 `자원/참고자료/...`로 바꿔 보니 판이 `v-f65e4ec1135d`에서 `v-421a7d14c81f`로 바뀌었다. 샘플 도면을 옮기거나 개발 작업 루트를 옮긴 뒤 다시 추출하면, 표본 구간은 "그래프 버전 불일치"로 막히고 사람이 확정한 `데이터/검토구간`·`분석결과`는 옛 판으로 처리된다(`study/nodes.py:220`, `study/results.py:370`). 고정값이 박힌 픽스처(`tests/fixtures/kg_algo`, `kg_context`)도 실패한다. 등록 기록의 `input_path`(`register/registry.py:99`)와 `svg_file`도 성질이 같다. §3 "논리 경로"가 이 문제를 다룬다.
4. **분석 기록의 경로는 기록일 뿐이다.** `analysis.json`의 `input_files[].path`는 실행 ID 계산에 쓰이지 않는다(`analysis/run.py:408`은 sha256만 묶는다). 옛 기록을 다시 쓸 필요가 없다. 백업 안 `이전보고.json`의 절대 경로도 이력이므로 그대로 둔다.
5. **사람이 한 작업이 git 밖에서 무방비로 섞여 있다.** `데이터/검토구간`·`분석결과`·`백업`은 ignore도 아니고 추적도 아니다. `git add -A` 한 번에 커밋되거나 `git clean -fd` 한 번에 지워질 수 있다.
6. **표본과 작업이 같은 폴더를 쓴다.** `데이터/구간`·`고정응답`·`지식/SNP-SAMPLE`은 git이 추적하는 표본인데, 앱은 같은 폴더에 사람의 작업을 쓴다. 개발 중 앱으로 표본 구간을 고치면 추적 파일이 바뀐다.
7. **`이탈후보/applicability-region-SNP-M-102-pzr.json`은 구간마다 생기는 판단인데 자원에 있다.** 지금은 표본 구간 하나뿐이라 문제가 안 되지만, 배포본에서 사용자가 새 구간의 적용 판단을 만들 곳이 없다. 이번 정리 범위 밖의 후속 과제로 남긴다(§5 D7).
8. **코드가 루트를 거치지 않는 곳이 많다.** 실행 코드(앱·스크립트·패키징·테스트)의 참조 중 `resource_path`·`work_path`를 거치는 것은 42건이다. 저장소 루트를 직접 붙이는 것이 52건, 상수·인자·픽스처 등 행만으로는 판단할 수 없는 것이 168건이다(`inventory/summary.md` "실행 코드의 접근 방식"). 개발 환경에서 두 루트가 같은 동안에는 잘못된 루트로 열어도 드러나지 않는다.
9. **APR1400 재구성 안내가 함께 ignore된다.** `.gitignore`가 `데이터/참고자료/APR1400_DCD/` 전체를 제외해서, 다시 만드는 법을 적은 `도면목록.md`(12 KB)와 `스크립트/`(16 KB)도 새로 받은 저장소에는 없다.

## 2. 고정해 둘 계약

두 안 모두 아래 두 가지는 바꾸지 않는다.

- **작업 루트 안의 배치는 그대로 둔다.** `<작업 루트>/데이터/<하위>`, `<작업 루트>/출력`, `<작업 루트>/자료저장소`는 배포본 사용자의 `%LOCALAPPDATA%\HAZOP` 배치와 같다. 이 배치를 바꾸면 배포본 사용자 데이터를 앱이 옮겨야 하는데, 얻는 것은 이름 정리뿐이다. 그래서 옛 배포본 데이터를 옮기는 기능도 필요 없다(§5 D4).
- **자원 루트 안의 배치는 바꿔도 된다.** 묶음 폴더는 판마다 새로 만들기 때문이다. 다만 구간 JSON에 저장된 옛 상대 경로(§1의 1번)는 계속 읽혀야 하므로 별칭 표를 `paths.py`에 둔다.

## 3. 목표 구조 두 안

### 안 A: `자원/`과 `작업/`을 저장소 최상위에서 나눈다 (권장)

```
HAZOP/
├─ 자원/                    자원 루트 기준. 읽기 전용, git 추적
│  ├─ 기준/                 배포본에 묶음
│  │  ├─ 이탈후보/  기준표/  패턴/
│  ├─ 참고자료/             배포본에 묶지 않음
│  │  ├─ HAZOP 기법/ (PDF는 ignore)  P&ID 기호 카탈로그/  P&ID 도면 샘플/  참고 사진/ (ignore)
│  │  └─ APR1400_DCD/        안내·스크립트만 추적, 원본·PDF는 ignore
│  └─ 표본/                 배포본에 묶지 않음. 시험·시연 때 작업 루트로 복사
│     ├─ 구간/  고정응답/  지식/SNP-SAMPLE/  평가기준/
└─ 작업/                    개발 환경의 작업 루트. 통째로 ignore
   ├─ 데이터/  구간/ 검토구간/ 분석결과/ 백업/ 지식/ 초기사건/ 도면수정/ 도면연결/ 잠재후보/
   ├─ 출력/  자료저장소/  logs/
```

- 개발 환경 작업 루트의 기본값이 저장소 폴더에서 `저장소/작업`으로 바뀐다. `작업/` 안 배치는 `%LOCALAPPDATA%\HAZOP`와 같다.
- 사람이 한 작업은 전부 `작업/` 한 곳에 있고 git이 보지 않는다. 표본은 `자원/표본/`에서 추적되고 앱이 직접 쓰지 않는다.
- 표본이 필요한 실행(개발 중 앱 실행, 검사 스크립트, 테스트)은 `scripts/seed_samples.py`로 작업 루트에 복사한다. 이 스크립트는 없는 파일만 복사하고 있는 파일은 건드리지 않는다. `packaging/verify_bundle.py:198`이 지금 하는 일을 함수 하나로 모으는 것이다.

### 안 B: 자원만 `자원/`으로 모으고, `데이터/`는 작업 폴더로 남긴다

```
HAZOP/
├─ 자원/
│  ├─ 기준/      이탈후보/ 기준표/ 패턴/             배포본에 묶음
│  └─ 참고자료/  (안 A와 같음)
├─ 데이터/       개발 환경 작업 루트는 저장소 폴더 그대로. 표본(구간·고정응답·지식·평가기준)은 추적,
│               사람 작업 폴더(검토구간·분석결과·백업·초기사건 등)는 .gitignore에 이름으로 추가
├─ 출력/  자료저장소/   (지금과 같음)
```

- 안 A의 ③a 단계만 하고 멈춘 모양이다. 표본과 작업이 같은 폴더를 쓰는 문제(§1의 6번)는 남는다.

**권장은 안 A다.** 사람 작업이 git 바깥 한 폴더에 모이고, 표본과 작업이 섞이지 않으며, 새 폴더 규칙이 표 한 줄로 끝난다. 그리고 개발 환경에서도 자원 루트와 작업 루트가 실제로 갈라지므로, 지금은 숨어 있는 "잘못된 루트로 연 경로"(§1의 8번)가 개발 중에 바로 드러난다. 안 B는 안 A의 ③a와 같아서, ③a만 끝내고 멈춰도 동작하는 상태가 된다. 그래서 순서는 ③a(안 B 상태) → ③b(안 A 완성)로 둔다.

검토했지만 빼 둔 안이 하나 있다. `데이터/` 안에 `데이터/자원/`·`데이터/작업/`을 두는 안이다. 이렇게 하면 작업 루트 안 배치가 `데이터/작업/구간`으로 바뀌어 배포본 사용자 데이터를 옮겨야 한다. 그렇지 않으면 저장소와 배포본의 배치가 서로 달라진다. 어느 쪽이든 얻는 것보다 잃는 것이 커서 뺐다.

### `paths.py` 폴더 표 (안 A)

```python
# (이름, 루트, 상대 경로, 배포본 묶음)
FOLDERS = {
    "이탈후보": Folder("resource", ("자원", "기준", "이탈후보"), bundled=True),
    "기준표":   Folder("resource", ("자원", "기준", "기준표"), bundled=True),
    "패턴":     Folder("resource", ("자원", "기준", "패턴"), bundled=True),
    "참고자료": Folder("resource", ("자원", "참고자료"), bundled=False),
    "표본":     Folder("resource", ("자원", "표본"), bundled=False),
    "구간":     Folder("work", ("데이터", "구간")),
    "검토구간": Folder("work", ("데이터", "검토구간")),

                       "데이터/패턴/": "자원/기준/패턴/", "참고자료/": "자원/참고자료/"}

def folder(name, *parts): ...            # 표의 루트 기준 절대 경로
def resolve_resource_rel(rel): ...        # 구간 JSON inputs의 옛 상대 경로를 새 경로로(읽을 때만, 파일은 고치지 않음)
def is_reference_sample(file): ...        # 추출 source.file이 옛·새 참고자료 아래인지
```

별칭은 무조건 바꿔 쓰지 않는다. 경로를 `/`로 맞추고 `./`를 걷어낸 뒤, 그 경로에 파일이 있으면 그대로 쓰고 없을 때만 별칭으로 푼다. 이 함수를 거쳐야 하는 곳은 `analysis/run.py`의 `_resolve`(64행), `analysis/candidate_edit.py:37`, `packaging/w4_flow.py`의 자원 경로 검사(106행)와 음성 검사(244행)다. 저장소의 표본 구간 JSON `inputs`는 ③a 전환 커밋에서 새 문자열로 바꾸고, 사용자 파일은 고치지 않는다.

**논리 경로(§1의 3번 대책).** 추출 JSON의 `source.file`, 등록 기록의 `input_path`·`svg_file`은 물리 위치가 아니라 논리 경로로 기록한다. `paths.logical_rel(path)`는 자원 쪽 참고자료 아래 파일이면 지금과 같은 `참고자료/<나머지>`를, 작업 루트 아래 파일이면 지금처럼 작업 루트 기준 상대 경로를 돌려준다. 그러면 샘플 도면을 옮기거나 개발 작업 루트를 옮겨도 추출 JSON의 바이트가 그대로라 판이 바뀌지 않는다. `hazop/app/data.py:214`의 `"참고자료/"` 접두 판정도 그대로 맞는다. 읽을 때는 `paths.resolve_logical(rel)`로 실제 위치를 찾는다. 판 계산식(`_graph_version`)과 `BUILDER_VERSION`은 건드리지 않는다. 이 장치는 ③a 표 도입 커밋에 들어가야 하고, 그 뒤 이전 전후로 샘플을 다시 추출해 판이 같은지 확인한다(§4).

`resource_path`·`work_path`는 그대로 두고 표가 그 위에서 동작한다. 화면 문구에 경로를 보여 줄 때도 표에서 만든다(`"구간 JSON(데이터/구간)"` 같은 문자열을 코드에 박지 않는다). ③ 세션은 `inventory_data_paths.py`의 `FOLDER_CLASS`를 이 표에서 읽게 바꿔, 분류 표가 두 곳에 생기지 않게 한다.

## 4. 이전 방식

### ③a 자원 통합 (저장소 안, 추적 파일 중심)

커밋 순서:

1. **표 도입 커밋.** `paths.FOLDERS`·별칭 함수·논리 경로 함수를 넣는다. `.gitignore`에는 새 위치 패턴(`자원/참고자료/참고 사진/`, `자원/참고자료/HAZOP 기법/*.pdf`, `자원/참고자료/APR1400_DCD/원본/` 등)을 미리 더하고 옛 패턴은 그대로 둔다. 이동 커밋이 ignore 파일을 새 위치로 옮기는 순간에도 권리가 불분명한 사진과 원본 PDF가 git에 드러나지 않게 하려는 것이다. 자원 쪽 참조(목록의 `class=자원`·`참고`·`대용량참고`, 실행 코드 부분)를 모두 표로 바꾼다. 표의 경로는 아직 옛 위치(`데이터/이탈후보`, `참고자료`)를 가리킨다. 테스트 전부 통과해야 한다.
2. **이동 커밋.** 먼저 `참고자료/`·`데이터/참고자료/`의 ignore 파일까지 포함한 sha256 목록을 만든다(③b와 같은 방식). 그다음 `git mv`만 한다. `참고자료/*` → `자원/참고자료/*`, `데이터/{이탈후보,기준표,패턴}` → `자원/기준/*`, `데이터/참고자료/APR1400_DCD` → `자원/참고자료/APR1400_DCD`(추적 안 된 폴더라 OS 이동). 옮긴 파일의 바이트는 그대로이므로 `git log --follow`가 100% 이름 바꾸기로 잇는다. 이 커밋 하나만으로는 테스트가 실패한다. 커밋 메시지에 "다음 커밋과 짝, 단독으로 bisect 대상 아님"이라고 적는다.
   이동 직후 `git status --ignored`로 사진·원본 PDF·APR1400 원본이 ignore로 잡히는지, 이동 전 목록과 sha256이 같은지 본다.
3. **표 전환 커밋.** 표의 상대 경로와 별칭 표, `.gitignore`(옛 패턴 삭제, APR1400 안내 파일은 추적), `build_package` 묶음 규칙(`DATA_DIRS`를 표에서 만듦), `verify_bundle`·`w4_flow`의 경로, 문서 경로를 고친다. `verify_bundle.py:350`의 참고자료 미포함 검사는 지금 `_internal/참고자료`만 본다. 새 위치 `_internal/자원/참고자료`와 `_internal/자원/표본`도 보게 바꿔야 실수로 묶었을 때 잡힌다. 테스트 통과, `inventory_data_paths.py` 결과, 샘플 재추출 판 비교로 확인한다.

이동 커밋에 내용 수정을 섞지 않는다는 규칙을 지키면 2번은 단독으로 테스트를 통과할 수 없다. 1번에서 표를 먼저 깔아 두었기 때문에 3번은 거의 표 몇 줄만 바뀐다.

### ③b 작업 데이터 분리 (사용자 데이터 이전)

새 스크립트 `scripts/migrate_work_root.py`가 한다. 기본은 미리보기이고 `--write`일 때만 쓴다.

0. **앱이 돌고 있으면 멈춘다.** 시작할 때 `.hazop-app.lock` 잠금을 잡아 본다. 잡지 못하면 앱이 옛 `데이터/`에 쓰는 중이므로 아무것도 하지 않고 끝낸다. 잠금 파일 자체는 옮길 목록에서 뺀다.
1. **목록.** `데이터/`(③a 뒤 남은 것), `출력/`, `자료저장소/`, `logs/`의 모든 파일을 추적·미추적·ignore 구분 없이 걷는다. 파일마다 상대 경로, 크기, sha256, git 상태를 `before.json`에 쓴다.
2. **행선지 표.** 추적 표본(`데이터/구간/region-SNP-M-102-pzr.json`, `고정응답/*`, `지식/SNP-SAMPLE/*`, `평가기준/*`)은 `git mv`로 `자원/표본/` 아래로 간다(별도 이동 커밋). 그 밖의 파일은 `작업/` 아래 같은 상대 경로로 간다. 추적 표본 중 HEAD와 내용이 다른 파일(예: 앱이 `candidate_edit`로 고친 표본 구간)은 사람 작업으로 본다. 이런 파일은 먼저 `작업/` 아래 같은 경로로 복사하고 백업에도 넣은 뒤에만 HEAD로 되돌린다. 미리보기는 행선지 표, 수정된 표본, 충돌(대상에 다른 내용 파일이 이미 있음)을 보여 주고 끝난다.
3. **통째 백업.** `--write`이면 먼저 저장소 밖 `%LOCALAPPDATA%\HAZOP-이전백업\<UTC 시각>-<번호>\`로 전부 복사한다. 폴더는 새로 만들 때만 쓰고(이미 있으면 번호를 올림) 기존 백업을 덮어쓰지 않는다. 백업의 sha256을 `before.json`과 대조해 하나라도 다르면 멈춘다. 저장소 밖에 두는 이유는 `git clean`이나 작업 트리 정리가 백업을 지우지 않게 하려는 것이다.
4. **옮기기.** 파일 단위로 `os.replace`를 쓴다(같은 볼륨). 대상에 같은 해시 파일이 이미 있으면 건너뛰고, 다른 해시면 그 파일은 옮기지 않고 보고한다. 원본은 지우지 않고 옮기기만 하며, 빈 폴더만 마지막에 정리한다.
5. **대조.** `after.json`을 만들어 `before.json`의 모든 파일이 행선지에 같은 sha256으로 있는지 본다. 하나라도 빠지면 실패로 끝내고 백업 경로를 알려 준다.
6. **표본 채우기.** `scripts/seed_samples.py`로 `자원/표본`을 `작업/데이터`에 채운다. 기본은 없는 파일만 복사하고, 이미 있는데 내용이 다른 파일은 목록으로 보고한다. `--refresh`를 주면 그 파일들을 백업한 뒤 표본으로 덮는다.
7. **옛 위치 경고.** 새 코드는 시작할 때 저장소 폴더의 옛 `데이터/`·`출력/`에 작업 파일이 남아 있으면 "이전되지 않은 작업이 있음"을 알린다. 옛 작업을 잊은 채 새 작업 루트에서 일하는 일을 막는다.

다시 돌려도 결과가 같다. 이미 옮긴 파일은 "원본 없음, 대상에 같은 해시"로 보여 건너뛴다. 중간에 멈춘 실행도 다음 실행이 남은 차이만 옮긴다.

**옛 배포본 데이터는 앱이 옮기지 않는다.** §2대로 작업 루트 안 배치가 바뀌지 않기 때문이다. 배포본 사용자의 구간 JSON에 남은 옛 자원 경로는 `resolve_resource_rel`이 읽을 때 풀어 준다.

### 이전 뒤 재발 방지 장치

- **경로 문자열 검사 테스트** `tests/test_path_literals.py`: `hazop/`·`scripts/`·`packaging/`·`tests/`의 `.py`를 AST로 읽어, 문자열 상수가 `데이터`·`참고자료`·`자원`·`작업`과 똑같거나 이 이름 뒤에 `/`·`\`가 붙어 있으면 실패한다. 모듈·함수 docstring은 뺀다. 허용 목록은 `hazop/paths.py`, `scripts/inventory_data_paths.py`, `scripts/migrate_work_root.py`, `scripts/seed_samples.py`와 이 테스트 자신이다. 사람이 매번 확인하지 않아도 테스트가 막는다.
- **두 루트 분리 테스트**: `HAZOP_RESOURCE_ROOT`와 `HAZOP_WORK_ROOT`를 서로 다른 임시 폴더로 두고(자원 쪽은 묶음과 같은 `자원/기준`만 복사, 작업 쪽은 `seed_samples`로 채움) 추출 → 그래프 → 구간 → 분석 → ⑤ 저장 → ⑥ 초기사건 저장까지 돈다. 옛 경로 문자열을 가진 구간 JSON으로도 한 번 돈다(별칭 확인).
- **배포본 확인**: `python scripts/build_package.py --out <저장소 밖> --build --with-check`, 그다음 `python packaging/verify_bundle.py --dist <...>/dist/HAZOP-verify --target-base <...> --out <...>`과 배포용 `--app-only`. 묶음 안에 `자원/기준`만 있고 `자원/참고자료`·`자원/표본`이 없어야 한다.
- **판 유지 확인**: 이전 전후에 샘플 도면 세 장을 다시 추출해 `graph_version`이 같은지 본다. 다르면 논리 경로가 빠진 곳이 있다는 뜻이다.
- **목록 전후 비교**: `inventory_data_paths.py`를 이전 전후에 돌려 `references.csv`에서 실행 코드의 `literal`·`repo_root` 참조가 `paths.py`와 허용 목록에만 남았는지 본다.

## 7. 범위 밖 발견 (후속)

- `hazop/study/migrate.py:240`의 백업은 폴더 이름이 초 단위 시각과 라벨뿐이라, 같은 초에 같은 파일을 다시 백업하면 `shutil.copy2`가 앞 백업을 덮어쓴다. `hazop/ie/store.py:102`는 같은 이름이 있으면 번호를 올린다. 이번 설계와 별개인 기존 결함이라 고치지 않았다. 저장 결함 묶음(공용 저장 함수)과 함께 다루는 것이 맞다.
- 목록 스크립트는 하위 폴더가 변수이거나(`os.path.join(ROOT, "데이터", sub)`), 튜플이 여러 줄에 걸치거나, f-string 안에 있으면 하위 폴더 없이 "루트"로만 센다. 접근 방식도 같은 행의 낱말로만 판단한다. 실행 코드의 빈틈은 이전 뒤 AST 검사 테스트가 막으므로 목록 쪽은 그대로 둔다.
