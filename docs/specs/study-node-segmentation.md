- 작성일 2026-11-13. 상태는 **규격 초안, 구현 전**입니다. 코드는 고치지 않았습니다. 코드 줄 번호는 커밋 `610fc72` 기준입니다.
- 사용자 결정 2026-11-13(DEC-0303·0304)을 받아 2026-11-09 설계(rev 0)를 고쳐 씁니다. rev 0의 본문과 측정은 지우지 않고 문서 끝 '부록 A'로 옮겼습니다. 부록 안의 '§' 번호는 부록 안의 절입니다.
- 채팅 창과 도구 호출 방식은 같은 날 D-chat 세션이 따로 정합니다(`docs/specs/` 아래 채팅 규격, 작성 중). 이 문서는 구간 도구가 무엇을 받고 돌려주는지까지만 정하고, 채팅이 도구를 어떻게 부르는지는 그 규격을 따릅니다.
- 추정은 그 자리에 [추론]으로 적었습니다. 수치는 출처 절을 함께 적었습니다.

## 1. 지금 코드가 전제하는 곳

'덮음률 100%'(A)와 '한 구성요소는 한 구간'(B)을 전제한 곳, 그리고 v2에서 뜻이 바뀌는 집합 단위 확정(C)과 스크리닝 제외 구간(D)을 셌습니다. '깨짐'은 v2 파일을 넣으면 틀린 값을 내거나 막히는 곳, '고침'은 동작은 맞지만 문구·뜻을 바꿔야 하는 곳, '그대로'는 이미 여러 구간을 다루는 곳입니다.

## 2. 저장 규격 v2

### 2.1 집합 문서

파일 자리는 그대로(`work/data/study-nodes/<프로젝트>/<graph_id>.json`)입니다.

```json
{
  "schema_version": "0.2",
  "kind": "hazop_study_nodes",
  "project_id": "...", "graph_id": "project-...", "graph_version": "...",
  "set_rev": 41,
  "nodes": [
    {"node_id": "S7", "name": "충전펌프 CV-PP01 토출", "rev": 3,
     "origin": "ai", "state": "confirmed",
     "members": ["..."],
     "design_intent": {"text": "...", "by": "ai", "batch_id": "B4"},
     "basis": "주요 장비 VCT-01 → 재생열교환기 HX-01",
     "boundary_hint": {"from": "entity-..", "to": "entity-.."},
     "batch_id": "B4",
     "confirmed": {"at": "...", "by": "홍길동", "rev": 3},
     "locked": null,
     "screen": {"score": 5, "grade": "주요"}}
  ],
  "batches": [
    {"batch_id": "B4", "origin": "ai", "at": "...", "request": "대표 구간 3~5개 만들어 줘",
     "chat_turn": "turn-..", "tool": {"name": "make_candidates", "params": {"granularity": "normal"}},
     "model": "claude-...", "ops": [{"op": "add", "node_id": "S7"}],
     "undone": null}
  ],
  "graph_member_refs": {"entity-..": "ref-.."}, "member_digest": "md3-...",
  "history": [],
  "legacy": {"from_schema": "0.1", "status": "confirmed", "confirmed_at": "...", "previous": []}
}
```

- 집합 머리에서 `status`·`confirmed_at`·`confirmed_by`를 뺍니다. 확정은 구간마다입니다. 일부러 빼는 이유는 §2.5의 '옛 앱이 새 파일을 덮어쓰지 않게'입니다.
- `set_rev`는 저장할 때마다 1 오르는 정수입니다. 채팅 도구가 '읽은 판'으로 쓰고(§6), 저장 충돌은 지금처럼 파일 지문(`store_io`)으로 막습니다.
- `graph_member_refs`는 구간 구성요소가 아니라 **그래프 전체** 구성요소의 안정 참조입니다(§1 #17·#18). `member_digest`는 구간마다 따로 셀 수 있게 판을 올립니다(§2.6).
- `proposer` 필드는 없앱니다. 어떤 도구를 어떤 값으로 불렀는지는 묶음(`batches[].tool`)에 남습니다.

### 2.2 구간 하나의 상태

| 필드 | 값 | 뜻 |
| --- | --- | --- |
| `origin` | `ai` · `user` · `script` | 누가 처음 만들었는가. `ai`는 채팅 요청으로 AI가 적용, `user`는 도면에서 고르기·병합·분할, `script`는 0.1 파일의 규칙 제안. 처음 값을 바꾸지 않음 |
| `state` | `applied` · `confirmed` · `locked` | 적용됨(미확정) → 확정 → 잠금 |
| `rev` | 1부터 | 구성요소가 바뀔 때만 1 오름. 이름·설계 의도만 바꾸면 그대로 |
| `confirmed` | `{at, by, rev}` 또는 null | 확정한 사람과 그때의 `rev` |
| `locked` | `{at, by, reason}` 또는 null | §5 |

```
applied ──확정(사람)──▶ confirmed ──잠금(사람)──▶ locked
   ▲                       │                        │
   └──확정 해제(사람)──────┘◀──잠금 풀기(사람, 이유)─┘
```

- **적용됨**: AI·사람·옛 규칙이 만든 그대로. ④에 보이고 도면에 칠해지지만 ⑤ 행은 없습니다. AI도 고칠 수 있습니다(단, 다른 요청 묶음이 만든 구간을 고치면 그 구간을 이번 묶음의 `edit`로 적어 둠).
- **확정**: 사람이 '이 구간으로 분석한다'고 정한 것. ⑤ 칸이 생깁니다. AI는 바꾸지 못하고 제안만 합니다(§6.5). 사람이 구성요소를 바꾸려면 '확정 해제'를 거칩니다. 해제해도 ⑤ 칸은 지우지 않고, 다시 확정할 때 `rev`가 바뀌었으면 그 구간 칸만 '범위 바뀜'이 됩니다(§2.4).
- **잠금**: §5.
- 확정은 '고른 구간 확정'과 '적용된 구간 모두 확정' 두 길로 합니다. 빈 구간과 그래프에 없는 구성요소는 지금처럼 확정을 막습니다(`nodes.py:446-454` 유지). 구간 밖 구성요소는 막지 않습니다.

### 2.3 묶음(batch)과 되돌리기

채팅 요청 하나, 도면에서 한 번 고르기, 병합 한 번이 각각 묶음 하나입니다. 묶음 ID는 `B1, B2, …`로 다시 쓰지 않습니다.

- `ops`의 종류는 `add`(새 구간), `edit`(구성요소·이름·설계 의도 변경, 바꾸기 전 구간 전체를 `before`에 적음), `remove`(구간 삭제, `before`에 구간 전체)입니다.
- **되돌리기**는 묶음 단위로만 합니다. `add`는 지우고, `edit`·`remove`는 `before`로 돌립니다. 되돌린 묶음은 `undone: {at, by}`를 적고 지우지 않습니다. 구간 ID는 다시 내지 않습니다(`issued_node_ids`가 묶음도 봄).
- 되돌리기를 막는 경우(모두 사람이 고를 수 있게 이유와 구간을 보임):
  1. 그 묶음이 만든·바꾼 구간 가운데 지금 `confirmed`·`locked`인 것이 있음. 사람이 먼저 확정을 해제해야 합니다.
  2. 뒤 묶음이 같은 구간을 다시 바꿨음. 뒤 묶음부터 되돌려야 합니다(가장 최근 묶음부터만 되돌리는 것이 아니라, 겹치는 뒤 묶음이 있을 때만 막음).
  3. 그 구간에 ⑤ 칸이 있음(확정한 적이 있음). 1과 같은 경우가 대부분이지만, 확정 해제 뒤에도 칸이 남아 있으면 막고 §4.4의 '구간이 사라질 때'로 넘깁니다.
- 묶음은 저장 파일 안에 최근 50개만 두고, 그보다 오래된 묶음은 `history`에 요약 한 줄로 줄입니다(되돌리기는 안 됨). [추론: 143쪽에서도 채팅 요청이 수백 번은 아니라고 봄]

### 2.4 ⑤ 결과와의 연결

지금은 결과 문서 하나가 집합 확정 시각 하나를 가리켜서(`results.py:400-403`), 구간 하나만 다시 확정해도 ⑤ 전체가 옛 결과가 되고 `remap.carry_saved`의 추정 대응으로 옮겨야 합니다. 겹침이 생기면 이 추정(#10·#11)이 틀립니다. 그래서 연결을 구간 단위로 바꿉니다.

- 결과 문서 머리: `study_nodes_ref` 대신 `{"graph_version", "schema": "0.2"}`.
- 칸마다 `node_rev`: 그 칸을 분석할 때 구간의 `rev`. 확정할 때 그 구간의 칸을 만들면서 적습니다.
- 칸을 열 때: 구간의 지금 `rev`와 칸의 `node_rev`가 같으면 그대로, 다르면 그 칸의 항목에 `scope_changed`를 붙이고 칸 상태를 `not_analyzed`로 돌립니다(항목은 지우지 않음. 지금 `remap`의 '범위 바뀜'과 같은 표시). `node_rev`를 지금 값으로 맞추는 일은 사람이 '다시 확인함'을 누를 때 합니다.
- 칸은 구간 ID로 찾습니다. 구간 ID는 확정 해제·다시 확정을 거쳐도 그대로라 옮길 일이 없습니다.
- 그래프 판 이전(`migrate.on_load`)은 지금처럼 결과의 `kg_paths`를 바꾸고, 내용이 바뀐 구간의 `rev`만 올립니다(§2.6).

### 2.5 옛 파일(0.1) 읽기

이전 스크립트를 따로 돌리지 않습니다. 읽을 때 메모리에서 0.2로 바꾸고, 처음 저장할 때 원본을 백업한 뒤 0.2로 씁니다.

| 0.1 값 | 0.2로 읽은 값 |
| --- | --- |
| 집합 `status: confirmed` | 모든 구간 `state: confirmed`, `confirmed: {at: 집합 confirmed_at, by: confirmed_by, rev: 1}` |
| 집합 `status: proposed` | 모든 구간 `state: applied` |
| 구간 `origin: rule` | `script` |
| 구간 `origin: merged`·`split`, AI 검토 받아들임 | `user` |
| 구간 `screen.status: excluded` | **구간 목록에서 숨기고** `legacy.excluded_nodes`로 옮김. 그 구성요소는 '구간 밖'이 됨 |
| 구간 `screen.status: low` | 그대로 두고 등급 '낮음' |
| `absorbed`·`parts` | `legacy`로 옮김(되돌리기 근거로 남김, 화면은 안 씀) |
| `previous` | `legacy.previous`. 0.1 결과를 처음 이을 때만 씀 |
| `member_refs`(구간 구성요소만) | 읽을 때 그래프 전체로 다시 셈. 판이 이미 바뀌었으면 지금처럼 재확인 |
| 결과 `study_nodes_ref`가 집합과 맞음 | 모든 칸 `node_rev: 1` |
| 결과 `study_nodes_ref`가 집합과 다름 | 지금 `remap.carry_saved`를 한 번 돌려 잇고(§4.4), 멈추면 지금처럼 사유를 보임 |

- **제외 구간에 ⑤ 칸이 있으면.** 0.1의 `empty_results`는 제외 구간에도 칸을 만들었습니다. 그 칸에 항목이 하나라도 있으면(사람이 꺼냈다가 다시 제외한 경우 등) 그 구간은 숨기지 않고 `applied` 구간으로 남겨 보입니다. 항목이 없으면 칸은 결과에서 지우지 않고 `archived_cells`로 옮깁니다.
- **백업.** 처음 0.2로 쓰기 직전에 `<이름>.v0.1.bak.json`을 남깁니다(결과 파일도 같음). 지금 `store_io.unused_name` 규칙을 씁니다.
- **옛 앱이 새 파일을 여는 경우.** 0.2 파일에는 집합 `status`가 없어 옛 앱의 형식 검사(`nodes.py:544`)가 실패하고, ④는 '읽을 수 없는 파일'로 처리해 덮어쓰기 전에 묻고 백업합니다(`study.py:1063-1095`). 옛 앱이 말없이 덮어쓰지 않는 것은 이 동작에 기대므로 N1 시험에 넣습니다.
- `schema_version`이 0.2보다 큰 파일은 읽지 않고 같은 경로로 보냅니다.

### 2.6 그래프 판이 바뀔 때

`migrate.plan`(`migrate.py:113-153`)은 지금 집합 구성요소만 보고 '새 판에 늘어난 구성요소'를 재확인 사유로 씁니다. 구간 밖 구성요소가 생기면 판이 바뀔 때마다 늘 재확인이 됩니다(#18). v2는 다음처럼 바꿉니다.

- 이름 바꿈 표는 그래프 전체 안정 참조(`graph_member_refs`)로 만듭니다. 늘거나 준 구성요소는 사유가 아닙니다.
- 내용 지문을 구간마다 셉니다(`md3-`): 그 구간 구성요소와 거기 닿는 물리 간선의 종류·태그·흐름·연결·정상 위치·고장 위치. 지문이 바뀐 구간만 `rev`를 올리고 확정 구간이면 상태를 `applied`로 내립니다(잠금 구간은 §5.3).
- 구간 구성요소가 새 판에서 사라졌으면 그 구간만 '재확인'이고 나머지 구간은 이어집니다.

## 3. 덮음률을 없앤 뒤의 표시

### 3.1 구간 밖 구성요소

- ④ KPI: "구간 22 · 확정 15 · 잠금 3 · 구간 밖 1,240(편차원 37)". 편차원은 rev 0의 정의(기기·밸브·인라인 부품·계기)를 씁니다. 구간 밖 편차원 수를 따로 보이는 이유는, 배관 조각이 구간 밖인 것은 흔하지만 밸브·기기가 구간 밖이면 놓친 것일 수 있기 때문입니다.
- 도면 전체 보기: 구간 밖 편차원만 점선 테두리로, 나머지 구간 밖 요소는 칠하지 않습니다. '구간 밖 모두 보기'로 전부 점선으로 바꿀 수 있습니다.
- 탐색기 ④: '구간 밖 N(편차원 M)' 한 줄. 누르면 구간 밖 편차원 목록.
- 확정·⑤·초기사건 인계는 구간 밖 수와 상관없이 됩니다(§1 #1·#31·#33·#36).
- 채팅에서 "아직 구간에 안 든 밸브는?"에 답할 수 있게 도구 `outside_components`를 둡니다(§6.2).

### 3.2 스크리닝 '제외 묶음'(D2)은 없앱니다

- 제외 묶음은 덮음률 100%를 지키려고 만든 장치였습니다(rev 0 §4.3, D2). 덮음률 규칙이 없어지면 '구간이 아닌데 구간처럼 저장되는 것'만 남고, ⑤ 행 숨기기·꺼내기·확정 때 확인 같은 예외 경로가 따라옵니다(§1 D 전제 9곳).
- 제외 묶음이 하던 '사람이 놓친 것을 볼 자리'는 §3.1의 '구간 밖 편차원'이 대신합니다. rev 0에서도 R3 제외에 편차원은 0개였고(부록 A.3.1), 제외로 간 편차원은 모두 범례 도면(R0)의 것이었습니다.
- R0(범례 도면 표시)는 그대로 둡니다. 표시한 도면의 구성요소는 도구가 후보를 만들지 않고, '구간 밖' 수에서도 따로 셉니다("구간 밖 1,240 · 그중 범례 도면 502").
- 0.1 파일의 제외 구간은 §2.5대로 숨깁니다.

## 4. 겹침의 영향

### 4.1 무엇이 겹치는가

- 겹침은 구성요소 단위입니다. 같은 밸브·배관이 두 구간에 들 수 있습니다. 관행상 경계 장비(주요 장비)는 양쪽 구간에 함께 드는 일이 흔합니다 [추론].
- 같은 구성요소 집합을 가진 구간이 둘 생기는 것은 막습니다(적용할 때 '같은 구간 있음'으로 거절). 하나가 다른 하나를 통째로 품는 것은 허용합니다(예: 계통 전체 구간과 그 안의 펌프 구간).
- 도면: 전체 보기에서 겹친 요소는 첫 구간 색 위에 두 번째 구간 색 줄무늬를 얹고, 배지에 "S7·S9"처럼 둘 다 적습니다(지금은 `webview.py:331`이 첫 구간 색만 칠함). 구간 하나를 고르면 그 구간만 강조하므로 겹침이 문제되지 않습니다.

### 4.2 ⑤ 워크시트

- 칸은 지금처럼 (구간, 편차)입니다. 겹친 구성요소는 두 구간의 칸에서 각각 원인·보호수단으로 적힐 수 있습니다.
- '같은 구성요소를 쓰는 다른 칸'(`related.py:272-276`)은 이미 구간 목록의 합집합을 봅니다. v2에서는 겹친 구간의 칸을 맨 위에 "겹친 구간 S9의 칸"으로 따로 묶어 보입니다. 같은 원인을 두 번 적었는지 사람이 보는 자리입니다.
- AI 일괄 분석은 구간마다 돕니다. 겹친 구간을 분석할 때, 겹친 다른 구간의 승인 항목 가운데 겹친 구성요소를 원인으로 쓴 것을 맥락으로 함께 넘깁니다(최대 10개). 같은 원인을 다시 적되 '이미 S9에서 다룸'을 근거에 남기게 하려는 것입니다 [추론: 프롬프트 효과는 구현 뒤 확인].
- Excel 내보내기는 구간마다 따로 적습니다. 겹친 구성요소에는 '겹침: S9' 열을 더합니다.

### 4.3 초기사건 인계 묶음

같은 원인이 두 구간에서 승인되면 지금은 후보가 둘 생겨(`bundle.py:383-389`) 초기사건이 두 번 셈될 수 있습니다.

- **같은 원인의 열쇠**: 항목의 `cause_refs`를 (안정 참조 `ref`, 고장 형태 `failure_mode` 없으면 `cause_kind`)의 집합으로 본 것. 집합이 같으면 같은 원인입니다. 편차는 열쇠에 넣지 않습니다(같은 펌프 정지가 S7에서는 '유량 없음', S9에서는 '압력 낮음'으로 나올 수 있음).
- **묶는 범위**: 두 항목이 모두 승인이고, 두 구간이 그 원인 구성요소를 함께 품을 때만 묶습니다. 겹치지 않은 구간에서 같은 원인이 나온 것은 묶지 않고 지금 경고 규칙대로 둡니다.
- **묶은 후보**: IEC는 ⑥ 문서의 것을 그대로 쓰고, 묶은 것들 가운데 구간 순서(집합 안 순서) 첫 항목의 IEC가 대표입니다. 대표 후보에 `merged_from: [IEC…]`, `node_ids: [S7, S9]`, `entry_ids`, `deviation_labels`를 적습니다. `trace`는 항목마다 한 줄씩 그대로 둡니다(근거가 사라지지 않게).
- **⑥ 그룹이 다를 때**: 묶인 IEC들이 서로 다른 ⑥ 그룹에 들어 있으면 묶음을 만들되, 두 그룹 모두의 `problems`에 "같은 원인 IEC-12·IEC-30이 다른 그룹에 있음"을 넣어 그룹 확정을 막습니다(총괄 위임 V-4).
- `cause_refs`가 없는 자유 글 원인은 묶지 않고, 정규화한 원인 글이 같으면 '같은 원인일 수 있음' 경고만 둡니다.

### 4.4 구간을 바꿨을 때(`remap`)

| 경우 | 처리 |
| --- | --- |
| 확정 해제 → 구성요소 고침 → 다시 확정 | 구간 ID가 같으므로 칸도 같음. `rev`가 올랐으면 그 구간 칸만 '범위 바뀜'(§2.4) |
| 두 구간 병합(A+B → A) | B의 칸 항목을 A의 같은 편차 칸으로 옮기고 '범위 바뀜'을 붙임. B 칸의 원래 상태는 A 칸의 `legacy_cells`에 남김(지금 `remap` 방식) |
| 구간 분할(A → A, C) | A의 칸은 A에 남고 '범위 바뀜'. C는 칸 없이 시작. 원인 구성요소가 모두 C로 간 항목은 화면이 "C로 옮길까요?"를 묻고 사람이 고름 |
| 구간 삭제(칸에 항목 있음) | 막음. 사람이 옮길 구간을 고르거나(후보는 구성요소가 많이 겹치는 순) '보관'을 고름. 보관한 칸은 결과의 `archived_cells`로 가고 ⑤·IE에서 빠지지만 지워지지 않음 |
| 구간 삭제(칸에 항목 없음) | 칸을 지움 |
| 0.1 결과를 처음 읽음 | 지금 `remap.carry_saved`를 한 번 씀. `owner`를 목록으로 바꾸고 같은 ID 구간을 먼저 맞춤(#10·#11) |

'가장 많이 겹치는 구간으로 자동으로 옮기기'는 0.1 결과 잇기에만 남기고 v2 편집에서는 쓰지 않습니다. 겹침이 생기면 '가장 많이 겹치는 구간'이 둘 이상이 되기 쉬워서, 사람이 승인한 항목을 엉뚱한 구간에 붙일 수 있기 때문입니다.

## 5. 잠금

### 5.1 무엇이 '분석을 마친' 구간인가

**정한 것(총괄 위임 V-1): 조건을 채운 구간을 사람이 잠근다.** 조건은 그 구간의 모든 편차 칸(지금 44개)이 `analyzed` 또는 `excluded`이고, 항목 가운데 '제안'(AI 초안, 사람이 아직 안 봄) 상태가 없는 것입니다. 조건을 채우면 ④·⑤ 구간 머리에 '잠글 수 있음'을 보이고 사람이 '분석 마침 · 잠금'을 누릅니다.

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| (a) 칸이 하나라도 확정되면 자동 잠금 | 빨리 보호됨 | 분석 중인 구간을 고치려면 계속 풀어야 함. 사실상 확정과 같아짐 |
| (b) 모든 칸이 끝나면 자동 잠금 | 사람 손이 안 듦 | 사람이 '끝났다'고 판단하지 않았는데 잠김. 편차 목록이 늘면(44 → 45) 저절로 풀려야 하는지 애매 |
| **(c) 조건을 채운 뒤 사람이 잠금(권장)** | '분석을 마쳤다'는 판단이 사람 기록으로 남음. 조건이 있어 덜 된 구간을 잠그지 않음 | 한 번 더 누름 |

편차 목록이 바뀌어 잠근 구간에 새 편차 칸이 생기면, 잠금은 그대로 두고 그 칸만 '잠금 뒤 생긴 칸'으로 보입니다. 그 칸을 분석하려면 잠금을 풀어야 합니다.

### 5.2 잠긴 구간에서 할 수 있는 일

| 하는 이 | 할 수 있음 | 할 수 없음 |
| --- | --- | --- |
| AI | 읽기, 채팅 답의 근거로 쓰기, 겹친 다른 구간 분석의 맥락으로 쓰기, 구간 검토 제안(`node_review`, 적용 안 됨) | 구성요소·이름·설계 의도 바꾸기, ⑤ 칸에 항목 더하기(일괄 분석은 잠긴 구간을 건너뜀), 묶음 되돌리기로 건드리기 |
| 사람 | 보기, 강조, Excel·초기사건 인계에 넣기, 항목에 의견(메모) 달기 | 구성요소·이름·설계 의도 고치기, 항목 상태(승인·기각) 바꾸기, 구간 삭제·병합·분할 |

새 구간이 잠긴 구간과 겹치는 것은 막지 않습니다. 잠긴 구간 자체는 바뀌지 않기 때문입니다.

### 5.3 푸는 길

- '잠금 풀기'는 사람만, 이유를 적어야 합니다. 풀면 `confirmed`로 돌아가고 `history`에 `unlock`(사람, 이유, 시각)이 남습니다. 구성요소를 고치려면 이어서 '확정 해제'를 합니다.
- 지금의 `reopen`(집합 확정 해제, `nodes.py:471-479`)은 구간마다의 '확정 해제'가 됩니다. 잠긴 구간은 바로 해제할 수 없고 잠금 풀기를 먼저 거칩니다.
- 그래프 판이 바뀌어 잠긴 구간의 지문이 달라지면(§2.6) 잠금을 저절로 풀지 않습니다. 구간을 '판 바뀜 · 잠금 유지'로 표시하고 ⑤·IE 인계에 경고를 붙입니다. 사람이 풀고 다시 확인할 때까지 결과는 그대로 둡니다. 말없이 풀면 '분석을 마쳤다'는 기록이 흐려지기 때문입니다.

## 6. AI가 쓰는 구간 도구

### 6.1 원칙

- 도구는 `hazop/study/node_tools.py`(새 파일, Qt 없음)의 순수 함수입니다. 채팅 계층(D-chat·S-conn)이 이 함수를 도구로 엽니다.
- 읽는 도구는 결과에 상한과 쪽 나누기(`cursor`)가 있습니다. 그래프를 통째로 보내지 않습니다.
- 쓰는 도구는 파일을 직접 쓰지 않고 '제안한 동작'(`apply_nodes`의 입력)을 돌려주고, 앱이 그 동작을 검증해 실행합니다(작업 계획 '지킬 것'). 아래 `apply_nodes`·`undo_batch`는 앱이 부르는 함수이고, AI에게는 같은 서명의 '동작 제안' 도구로 보입니다.
- 모든 도구는 `set_rev`(읽은 판)를 받습니다. 저장된 판과 다르면 실행하지 않고 "구간이 그 사이 바뀜"을 돌려줍니다.

### 6.3 대표 구간 3~5개 → 나머지

1. 사람이 채팅에 "구간 나눠 줘"류를 적으면, AI는 `find_major_equipment`와 `make_candidates`(scope 없음 또는 사람이 말한 범위, `limit` 30)를 부릅니다.
2. AI는 후보 가운데 서로 다른 계통·도면에 걸치고 등급이 '주요'인 것 3~5개를 고르고, 이름과 설계 의도 초안을 적어 `apply_nodes`를 제안합니다. 앱이 바로 적용합니다(DEC-0303, 승인 전 적용). 답 카드에 고른 이유와 '이 요청 되돌리기'를 보입니다.
3. 사람이 확인합니다. 고치거나("이건 더 크게", "펌프는 따로"), 그대로 확정하거나, 되돌립니다. AI는 사람이 고친 차이(묶음의 `edit`)를 다음 요청의 맥락으로 받습니다.
4. 사람이 "나머지도"라고 하면 AI는 같은 매개변수(사람이 고친 크기 조절이 있으면 반영)로 `make_candidates`를 `skip_existing`으로 쪽을 넘기며 부르고, 쪽마다 `apply_nodes` 묶음 하나를 제안합니다. 쪽 하나가 묶음 하나라, 일부만 되돌릴 수 있습니다.
5. 나머지를 시작하기 전에 예상 호출 수와 시간을 보이고 확인을 받습니다(§6.4). 상한을 넘으면 범위를 나눠 달라고 합니다(총괄 위임 V-3).

'의미 있는 구간'(옛 D3)은 AI가 후보를 고를 때의 기준으로 남습니다: 편차원이 없는 후보(등급 '낮음')는 이웃 후보에 붙이거나 묶음의 끝으로 미루고, 범례 도면 후보는 만들지 않습니다.

| 구간 표기(`span.annotate`, 경계 색인) | 0.32초 | 부록 A.5.2 시제품 1회. 지금 코드는 `_segment_ends`를 한 번만 만들어 넘김(`span.py:144-160`) |
| 프로젝트 그래프 첫 짓기 | 처음 들어갈 때 ② 2.00초에 포함 | 부록 A.5.8, 부하 4~56% |
| AI 호출 하나(⑤ 칸 분석 값을 빌림) | 중앙 31.7초, p90 76초. 동시 2의 처리량은 동시 1의 약 1.4배 | 부록 A.4.7(U5 실측 2026-11-09). 구간 호출을 직접 잰 값은 아님 |

- 도구 자체는 143쪽에서 한 번에 1~2초라 채팅 응답 시간을 거의 정하지 않습니다. `make_candidates`는 같은 (graph_version, 매개변수)면 후보를 캐시해 쪽을 넘길 때 다시 자르지 않습니다.
- 시간을 정하는 것은 AI 호출 수입니다. 대표 구간은 호출 1~2번(약 1분)입니다. 나머지는 호출 하나에 후보 20개의 이름·설계 의도를 쓴다고 보면, 143쪽 C6 남긴 구간 1,793개(부록 A.3.1) 기준 약 90번, 동시 2에서 약 34분(느리면 약 80분)입니다 [추론: 호출당 후보 수 20은 아직 정하지 않은 값].
- 그래서 '나머지'는 범위(도면·계통)를 받아 나누어 돌리는 것을 기본으로 합니다. 한 요청의 상한은 D-chat 규격의 질문당 호출 상한을 따르고, 넘으면 AI가 범위를 나누자고 답합니다.
- APR1400 5.1.2-1처럼 기기를 못 알아본 도면은 `find_major_equipment`가 거의 빈 목록과 `unrecognized_equipment`를 돌려줍니다. 이때 후보는 크기 예산(40)으로만 잘리므로, AI는 답 카드에 "주요 장비를 못 찾아 크기로 나눔"을 알려야 합니다.

### 6.5 기존 AI 구간 검토(`node_review.py`)

- 확정·잠금 구간에는 AI가 적용하지 못하므로, 이 구간들에 대한 AI 의견은 지금 `node_review`의 '제안 → 사람이 받아들이기' 길로 갑니다. 받아들이면 사람 묶음(`origin: user`)으로 적용합니다(확정 구간이면 먼저 해제를 묻습니다).
- `screen_change` 판정(제외·낮음으로 옮기기)은 없앱니다. `merge`·`split`·설계 의도만 남깁니다.

## 7. 주요 장비와 크기 조절

### 7.1 주요 장비

경계가 되는 장비입니다. `segment.part_of`(`segment.py:73-87`)의 몫을 씁니다.

| 크기 | 경계가 되는 몫·kind | 기본 구성요소 예산 | 합치기 상한 |
| --- | --- | ---: | ---: |
| 크게(`coarse`) | 용기류(`VESSEL`) 가운데 원자로용기·증기발생기·가압기·탱크·응축기만 | 80 | 120 |
| **보통(`normal`, 기본)** | 용기류 전부(`EQUIPMENT_PART`의 `VESSEL` 11종) + 터빈·압축기 | 40 | 60 |
| 잘게(`fine`) | 보통 + 펌프·필터 + 제어밸브·안전밸브(`valve` 가운데 `control`·`relief`·`safety`가 든 kind) | 20 | 30 |

- '보통'의 용기류는 D1 그대로이고, 터빈·압축기를 더한 것이 바뀐 점입니다. 터빈·압축기는 지금 `MACHINE`(경계 아님)이라 앞뒤 배관과 한 구간이 되는데, 사용자가 말한 '주요 장비'에 가깝다고 봤습니다. 팬은 공조 계통에 많아 넣지 않았습니다 [추론](총괄 위임 V-6).
- '크게'의 예산 80·상한 120과 '잘게'의 20·30은 재지 않은 값입니다. N3에서 SNP·APR 5장으로 구간 수와 최대 크기를 재고 고칩니다(부록 A.7 D4는 '보통'만 잼).
- 기기를 못 알아본 것(`unrecognized_equipment`)은 경계가 되지 않습니다. 추출 품질(작업 계획 가. 도면 읽기 품질)이 좋아지면 저절로 줄어듭니다.

### 7.2 채팅 요청을 매개변수로

| 채팅 표현(예) | 도구 매개변수 |
| --- | --- |
| "크게", "계통 단위로" | `granularity` 한 단계 위로 |
| "잘게", "펌프는 따로" | `granularity` 한 단계 아래로, 또는 `extra_boundaries`에 펌프들 |

| "S7과 S8 합쳐" | `apply_nodes` `edit`(S7에 S8 구성요소 더함) + `remove`(S8) |

- 크기 매개변수는 묶음(`batches[].tool.params`)에 남깁니다. 다음 '나머지' 요청은 가장 최근에 사람이 고치지 않고 둔 묶음의 매개변수를 기본으로 씁니다.
- 낱말을 매개변수로 바꾸는 일은 AI가 합니다. 앱은 매개변수 값의 범위만 검사합니다.

## 10. 가장 위험한 곳

데이터를 잃거나 판정이 틀릴 수 있는 경로입니다. N1 검토는 이 경로를 재현 스크립트로 확인하기 전에는 경미로 낮추지 않습니다(CLAUDE.md 규칙 3).

1. **⑤ 결과와 구간의 연결(#12·#16·#34).** 지금 구조에서 구간 하나를 더하거나 다시 확정하면 결과 전체가 '옛 확정본 것'이 되고, `carry_saved`가 추정 대응으로 옮깁니다. 겹침이 생기면 그 추정(`remap.py:48` 사전 덮어쓰기, `:56` 같음 판정)이 사람이 승인한 항목을 다른 구간에 붙이거나 '범위 바뀜'으로 떨어뜨립니다. §2.4의 칸 판 번호가 이 경로를 없앱니다.
2. **0.1 파일 첫 저장(§2.5).** 읽을 때 바꾼 값으로 덮어쓰므로, 바꾸는 규칙에 틀린 것이 있으면 원본이 사라집니다. 백업을 먼저 쓰고, 백업을 못 쓰면 저장하지 않습니다.
3. **옛 앱이 0.2 파일을 여는 경우.** 옛 앱의 '읽을 수 없음' 처리에 기댑니다. N1 시험 ⑥으로 확인합니다.
4. **묶음 되돌리기(§2.3).** 사람이 그 사이 고친 구간을 AI 묶음 되돌리기가 덮으면 사람 작업이 사라집니다. 뒤 묶음 검사와 확정 구간 검사가 막습니다.
5. **구간 삭제·병합(§4.4).** 칸에 항목이 있는 구간을 지우면 항목이 사라집니다. 막고, 옮길 곳 또는 보관을 사람이 고르게 합니다.
6. **초기사건 이중 계산(#27, §4.3).** 데이터를 잃는 것은 아니지만, 겹친 두 구간의 같은 원인이 후보 둘이 되어 인계 묶음의 빈도·범주 수가 부풀 수 있습니다.
7. **그래프 판 이전의 늘 재확인(#17·#18).** 데이터를 잃지는 않지만, 구간 밖 구성요소가 하나만 있어도 판이 바뀔 때마다 모든 확정이 풀립니다.

### A.1 지금 구간 제안은 이렇게 돈다

`hazop/study/nodes.py`의 `propose(graph)`가 프로젝트 그래프(도면 그래프를 도면 연결점으로 이은 하나의 망) 하나를 받아 구간 목록을 돌려줍니다. 결정적이고 순수 함수입니다. 제안기 판은 `0.1.0`, `MAX_ACTIVE = 5`입니다(`nodes.py:23-24`).

1. 역할을 셋으로 나눕니다. `category`가 `equipment`면 기기, `instrument`면 계기, 나머지(배관 구간·밸브·T·캡·연결점·인라인 부품·**미분류**)는 모두 공정 요소입니다.

3. 공정 요소만 남긴 물리 연결(`has_endpoint`)의 연결 성분이 '기기 사이 배관 경로'입니다. 경로를 BFS 순서로 훑으며 분할 가중 요소(밸브·펌프)가 5개를 넘으면 자릅니다.
4. 계기는 계측·신호 연결을 따라 가장 가까운 구간에, 연결이 없으면 같은 도면에서 위치가 가장 가까운 구간에, 그래도 없으면 '기타'에 붙습니다.

#### A.3.2 판정

- **C2(분기점 사슬)는 버립니다.** 원 구간이 가장 많고(143쪽 20,458), SNP에서도 T마다 헤더를 잘라 스크리닝 뒤 48구간으로 C0보다 많습니다. 스크리닝이 다시 합쳐야 하는 양이 커서(143쪽 9,982개) '그래프로 자른다'는 뜻이 약해집니다.
- **C3(기기 중심 보로노이)는 SNP에서 가장 보기 좋지만 큰 도면에서 무너집니다.** SNP 21구간, 편차원 없는 구간 0입니다. 그러나 기기를 못 알아본 도면은 경로 전체가 한 구간으로 남고(143쪽 최대 652), 분할 가중 요소 수 제한이 없어 5개를 넘는 구간이 11개 생깁니다. 경계가 '거리의 절반'이라 사람이 경계를 설명하기도 어렵습니다. 같은 거리일 때 어느 기기에 붙일지가 실행 환경의 집합 순서에 따라 달라져(측정 중 SNP 값이 바뀜) 결정성도 따로 맞춰야 합니다.
- **C4(커뮤니티)는 비교용으로만 남깁니다.** 크기는 고르지만 경계가 기기·밸브와 맞지 않아 구간마다 '왜 여기서 끊었는가'를 적을 수 없습니다. 근거(`basis`)를 남겨야 하는 HAZOP 기록과 맞지 않습니다.
- **C5·C6가 남습니다.** 둘 다 C0의 경계를 물려받아 근거 문장을 그대로 쓸 수 있고, 거대 구간이 없어지며(원 최대 48, 뒤 최대 60), 끊긴 구간이 없고, 시간은 C0과 같습니다. 차이는 펌프·필터를 경계로 볼지입니다.
  - C5는 SNP 원 구간이 C0과 똑같아(45, 41) 회귀 기준이 흔들리지 않습니다.
  - C6는 '3단계 후속'에서 지적한 '펌프·필터마다 구간'을 없앱니다. SNP-M-201(CVCS)만 보면 C0+스크리닝 9구간 → C6+스크리닝 7구간이고, 충전펌프 CV-PP01이 밸브 CV-V201·V202, 유량전송기 CV-FT204와 한 구간(10개)이 되며, 필터 CV-F01은 압력조절밸브 CV-PV201 구간에 들어갑니다.
- **권장: C6.** HAZOP 노드는 '설계 의도가 하나인 묶음'이고 펌프는 흡입·토출 배관과 함께 보는 일이 많습니다 [일반지식, 출처 미확인]. 결정 항목 D1로 올립니다.

#### A.4.4 사람이 고치는 경로(④)

- 구간 카드에 등급 칩(주요·일반·낮음)을 보입니다. '스크리닝 제외' 구간은 목록 맨 아래에 접어 두고 "제외 N개 조각 · 구성요소 M개"로 셉니다.
- **꺼내기.** 제외 묶음에서 조각을 골라 '구간으로 꺼내기'. 조각 경계는 `parts`로 압니다. 묶음에 조각이 하나뿐이면 지금 `split`(일부만 뗄 수 있음)으로는 안 되므로, 묶음의 `screen` 상태만 `keep`으로 바꾸는 연산을 새로 둡니다.
- **떼기.** 합쳐진 조각은 '합친 조각 떼기'. 경계는 `absorbed`로 압니다(지금의 `split`).
- **옮기기.** 남은 구간도 '스크리닝 제외로 옮기기'를 할 수 있습니다. 이유를 꼭 적습니다.
- **확정 때 확인.** 확정 대화상자에 "스크리닝 제외 N개 조각(구성요소 M개)을 확인했음" 체크를 둡니다. 체크해야 확정합니다. 제외가 0이면 보이지 않습니다.
- **다시 제안.** '새 규칙으로 다시 제안'은 사람이 바꾼 판정(`by: "human"`)을 구성요소 기준으로 다시 적용합니다. 구성요소가 사라졌으면 그 판정은 버리고 알립니다.

#### A.4.6 기존 사람 확정 구간과의 호환

지금 판 이전(`migrate.plan`, `hazop/study/migrate.py:114`)은 **그래프 판이 바뀌었을 때** 확정본의 구성요소가 새 판과 하나도 빠짐없이 1:1로 대응할 때만 확정을 옮기고, 아니면 재확인으로 넘깁니다. 분할 규칙(제안기 판)은 그래프 판에 들어가지 않으므로, 규칙을 바꾸는 것만으로는 확정본이 재확인으로 넘어가지 않습니다. 문제는 사람이 새 규칙을 적용하려고 다시 제안할 때입니다.

**지금 코드에서 다시 확정하면 일어나는 일(확인함).** ⑤ 결과는 만든 확정본의 (`graph_version`, `confirmed_at`)을 기록합니다(`results.is_stale`, `hazop/study/results.py:374`). '확정 해제 → 다시 제안 → 확정'을 하면 `confirmed_at`이 바뀌어 옛 결과가 '이전 확정본으로 만든 것'이 되고, ⑤는 **빈 결과로 시작**하며 옛 파일은 첫 저장 때 보관본으로 옮겨집니다(`hazop/app/screens/results.py:1130-1148`). 사람이 승인한 항목이 화면에서 모두 사라집니다. 결정로그 155·160의 '범위 바뀜 · 다시 확인' 규칙은 도면별 결과를 프로젝트로 옮길 때(`span.migrate_results`)에만 있고 이 경로에는 없습니다. 새 분할을 들이려면 이 빈자리를 메워야 합니다.

- **확정본은 자동으로 다시 제안하지 않습니다.** 옛 파일에는 `screen`이 없으니 모두 `keep`으로 보입니다. 그래프 판이 바뀌었을 때의 재확인은 지금처럼 `migrate.on_load`가 맡습니다.
- **제안 상태 저장본**은 그대로 열고, ④ 머리에 "새 분할 규칙(0.2.0)으로 다시 제안할 수 있음"을 알립니다. 누르기 전에는 바꾸지 않습니다.
- **다시 제안할 때는 구간 대응표를 먼저 보여 줍니다.** 옛 구간과 새 구간을 구성요소 집합으로 맞춰 나눕니다.
  - 같음: 구성요소 집합이 똑같음. 옛 구간 ID·이름을 그대로 씁니다.
  - 합쳐짐: 새 구간이 옛 구간 여럿을 품음(예: 기기 구간 + 출구 배관). 첫 옛 ID를 남기고 나머지는 `legacy_ids`에 적습니다.
  - 나뉨·넓어짐·좁아짐: 겹치지만 같지 않음. 새 ID를 주고 `legacy_ids`에 옛 ID를 적습니다.
  - 제외로 감: 옛 구간 구성요소의 대부분이 '스크리닝 제외'로 감. 옛 ⑤ 결과가 있으면 자동으로 옮기지 않고 그 구간을 제외 묶음에서 꺼낼지 사람에게 묻습니다. 겹침이 가장 큰 구간으로 옮기는 지금 `span.legacy_map` 방식을 그대로 쓰면 결과가 행 없는 제외 구간으로 가서 보이지 않게 되기 때문입니다.
- **⑤ 결과 칸 이전(새로 만듦, S5).** 다시 확정할 때 옛 결과를 빈 결과로 버리지 않고 칸 단위로 옮깁니다. '같음' 구간의 칸은 상태·항목을 그대로 잇고 `study_nodes_ref`만 새 확정본으로 바꿉니다. '합쳐짐·나뉨·넓어짐·좁아짐' 구간의 칸은 결정로그 155·160과 같은 규칙으로 '범위 바뀜 · 다시 확인'을 붙이고 옛 '분석함·제외' 상태를 물려받지 않습니다. 대응 없는 옛 칸이 있으면 쓰지 않고 멈춥니다. 옛 파일은 지금처럼 보관본으로 남깁니다. 결정 항목 D11.
- **사람 확인 흐름.** 대응표에서 '같음'이 아닌 줄을 사람이 훑고 '이대로 적용'을 눌러야 새 제안이 저장됩니다. 적용 전 저장본은 지금 백업 규칙(`data/backup/<시각>-…`)으로 남깁니다. 적용 뒤에는 제안 상태라 다시 확정해야 ⑤를 씁니다.
- 대응표 계산은 구성요소 ID 집합 비교라 결정적입니다. 143쪽 1,800구간에서의 시간은 재지 않았습니다 [추론: 집합 연산이라 1초 미만].

#### A.4.7 선택 단계: AI 구간 검토(구독 AI 연결 뒤)

사용자 의도(2026-11-09): 처음 구간 설정은 AI 없이 그래프 알고리즘으로 하고, 그다음에 AI가 구간을 검토하는 단계를 넣어도 좋다. AI 결과는 늘 초안이고 사람이 확정합니다(결정로그 17·122·130). 이 단계는 선택이며, 없어도 ④ 흐름은 그대로 돕니다.

**흐름.** 그래프 분할·스크리닝(규칙) → (선택) AI 구간 검토 → 사람이 제안을 받아들이거나 고침 → 확정.

**AI에게 보여 줄 것(구간 하나 또는 이웃 구간 묶음 단위).**
- 구간 구성요소 목록: 종류·태그·배관 번호·출처 도면, 경계 기기(`boundary`), 이웃 구간 ID와 닿는 구성요소
- 스크리닝 판정과 점수·등급, 규칙이 붙인 조각(`absorbed`)
- 도면 연결점과 상대 도면
- 지식그래프에 있는 해당 기기 설명·운전 조건(있을 때만)

**AI에게 물을 것.**
1. 경계가 설계 의도 하나에 맞는가(예: 펌프와 토출 배관이 다른 구간으로 갈라졌는가)
2. 병합·분할 제안: 합칠 구간 ID 목록, 또는 떼어 낼 구성요소 목록과 이유
3. 스크리닝 판정에 대한 이견: 제외·낮음인데 봐야 할 구간, 남겼는데 뺄 만한 구간
4. 설계 의도 초안 한두 문장(⑤ 워크시트 '설계 의도' 칸의 초안으로 넘김)

**출력 형식(구조화 JSON).**

```json
{"node_id": "S7", "verdict": "ok|merge|split|screen_change",
 "merge_with": ["S8"], "split_off": [{"members": ["..."], "name": "..."}],
 "screen_to": "keep|low|excluded", "design_intent": "...", "reason": "...",
 "evidence": ["구성요소 ID 또는 지식그래프 근거 ID"]}
```

- 제안은 구간 파일에 바로 쓰지 않고 `ai_review` 묶음(구간 ID, 제안, 모델·시각, 입력 지문)으로 따로 둡니다. 입력 지문(구간 구성요소·이웃 지문)이 바뀌면 그 제안은 '오래됨'으로 보입니다.
- 근거 검증: `evidence`와 `merge_with`·`split_off`가 실제 구간·구성요소를 가리키는지 앱이 확인하고, 아니면 그 제안을 버리고 이유를 남깁니다(⑤ AI 근거 검증과 같은 방식).
- 사람이 '받아들이기'를 누르면 지금의 `merge`·`split`·스크리닝 옮기기 연산이 돌고 `history`에 `ai_review_accept`(제안 ID)를 남깁니다. '고쳐서 받기'와 '기각'(이유 선택)도 둡니다.

**규칙 결과와 AI 제안이 다를 때 보이는 방법.**
- ④ 구간 카드에 'AI 제안' 칩을 붙이고, 누르면 규칙 판정과 AI 제안을 나란히 보입니다(예: "규칙: 이웃 S8에 붙임(R2) · AI: 따로 둠, 이유 …").
- 도면 위에서는 제안한 경계를 점선으로 겹쳐 그립니다.
- 탐색기 ④ 묶음에 'AI 제안 N건 · 미처리 M건'을 보입니다. 미처리 제안이 있어도 확정은 막지 않고, 확정 대화상자에 남은 수를 알립니다.

**구독 호출 규모 추정.** 호출 수 = ⌈남긴 구간 수 ÷ 호출당 구간 수⌉ + 제외 묶음 수(도면당 1건, '꺼낼 조각이 있는가'만 물음). 아래는 호출당 10구간으로 계산한 값입니다.

| 자료(C6 + 스크리닝) | 남긴 구간 | 제외 묶음 | 호출 수 |
| --- | ---: | ---: | ---: |
| SNP 6장 | 29 | 0 | 3 |
| APR 5장 | 88 | 4 | 9 + 4 |
| APR 143쪽 | 1,793 | 141 | 180 + 141 |

호출당 시간은 U5(구독 실측, 2026-11-09)의 ⑤ 칸 분석 호출 값을, 사용량은 아래 두 실측의 범위를 빌려 씁니다. 구간 검토 호출의 프롬프트 크기가 비슷하다고 본 추정이며, 구간 검토를 직접 잰 값은 아닙니다.

- Opus 5.5(effort high) 호출당 중앙 31.7초, p90 76초. 동시 2의 실효 처리량은 동시 1의 약 1.4배(2배가 아님).
- 총 시간 ≈ 호출 수 × 31.7초 ÷ 1.4(동시 2 이상, 동시 1이면 ÷ 1. 느린 호출이 많으면 76초로 계산). 구독 7일 사용률은 호출 1회에 약 0.013~0.027%p 오릅니다. 두 실측값이 다르고 원인은 확인하지 못했습니다: U5 계통 실행 150회에 0.12→0.16(회당 약 0.027%p, 2026-11-09), 초기사건 계통 실행 745회에 0.25→0.35(회당 약 0.013%p, 2026-11-10 총괄 보고). 실행 확인 창은 이 범위로 보입니다.
- 예: APR 143쪽 전체(321회)는 약 2시간(느리면 약 5시간), 7일 사용률 약 +4.2~8.7%p. SNP 6장(3회)은 약 2분.
- 제외 구간은 도면당 묶음이 아니라 구간 하나에 1회입니다(사람이 옮긴 제외 구간도 따로 셈).

**구현(S6, 2026-11-10).** `hazop/study/node_review.py`(호출 단위·요청·검증·제안 묶음, Qt 없음), ④ '스크리닝' 메뉴의 'AI 구간 검토…'·'고른 구간만 AI 검토…', 고른 구간 카드의 'AI 제안' 상자(규칙 판정과 AI 제안 나란히, 받아들이기·고쳐서 받기·기각), 목록 행의 'AI 제안' 표시, 탐색기 ④ 묶음의 'AI 제안 N · 미처리 M', 확정 토스트의 미처리 수. 연결은 ⑤와 같은 클라이언트·멈춤 규칙(providers.halts)을 씁니다. 제안 묶음은 `data/study-nodes/<프로젝트>/구간AI검토-<graph_id>.json`입니다. 받아들인 설계 의도는 ⑤ '설계 의도' 칸에 'AI 초안'으로 보입니다.

**지식 맥락(단위 G, 2026-11-11).** 지식그래프가 있고 지금 도면 판과 맞으면 구간마다 `knowledge` 목록을 붙입니다. 정한 것은 세 가지입니다.

1. 넣는 항목과 상한. 구간 구성요소에 적용 관계(⑤ 지식 맥락과 같은 3종, V4만)로 닿는 확인된 지식 노드만 넣습니다. 항목은 지식 ID, 종류, 이름·문구·항목·값·단위·압력 기준·운전 모드(값이 있는 것만), 닿는 구성요소 ID(최대 5개)입니다. ⑤ 지식 맥락과 같이 미확인 칸(`unknown_fields`)과 값이 다른 항목(`conflict_with`, 도면과 다르면 `conflict_with_drawing`)을 함께 보냅니다(미확인은 미확인으로, 충돌은 고르지 않고 둘 다). 구간당 최대 8개이고, 이름·문구는 200자(완성형으로 셈)에서 자르고 끝에 '…'을 붙이며, 결합 문자나 이음 문자로 묶인 글자 가운데에서는 자르지 않습니다. 순서는 구성요소 순서, 지식 종류 순서, 지식 ID 순서라 같은 입력이면 요청 바이트가 같습니다. 넘친 수는 `knowledge_omitted`로 알립니다. 지식 항목이 없는 구간의 맥락은 이 필드가 없습니다.
2. 오래됨 판정. 제안에 `knowledge_fp`(그 구간에 보인 지식 항목의 해시, 없었으면 null)를 따로 적습니다. `kg_version`은 넣지 않습니다. 지식그래프를 다시 지어도 그 구간에 보인 항목이 그대로면 제안은 살아 있고, 그 항목이 바뀌거나 생기거나 없어지면 '오래됨'이 됩니다. 이 필드가 없는 옛 제안은 지식으로는 판정하지 않습니다. ④ 화면은 지식 색인을 프로젝트 그래프와 지식그래프 포인터 파일(`current.json`)의 지문으로 기억하므로, 지식그래프를 다시 지으면 다시 읽고 검토를 돌릴 때는 늘 다시 읽습니다.
3. 근거. `evidence`는 그 구간에 붙은 지식 ID를 가리켜도 됩니다(오래됨 판정이 보는 범위와 같게, 같은 호출의 다른 구간 항목은 받지 않습니다). 보이지 않은 지식 ID를 든 제안은 버리고 이유를 남깁니다.
4. 도면 근거(INTENT §2 '도면에 없는 설비를 전제로 한 AI 가설은 하지 않는다'). 구간 구성을 바꾸는 제안(병합·분할·판정 변경)은 `evidence`에 도면 근거가 하나 이상 있어야 합니다. 도면 근거는 구성요소 ID와 구간 ID입니다(구간은 도면 구성요소의 묶음이라 도면 근거로 봅니다). 지식 ID는 보조 근거로만 받습니다. 이유·설계 의도·새 구간 이름에 든 태그 모양 낱말(대문자와 숫자를 '-'로 이은 것)이 프로젝트 도면의 태그·배관 번호·도면번호에 없으면 그 제안을 버리고 '도면에 없는 태그'로 남깁니다. 구간을 바꾸지 않는 설계 의도 초안은 지식 근거만으로 받고, ⑤에서 'AI 초안'으로 보입니다.

**고쳐서 받기(단위 G).** 병합 제안은 합칠 구간을 고르고(제안한 구간과 이웃 구간 가운데), 분할 제안은 떼어 낼 구성요소를 고릅니다. 받으면 지금의 `merge`·`split` 연산이 돌고 `history`의 `ai_review_accept`에 제안 ID와 고친 내용(`changes`)이 남습니다. 결과 구간은 같은 편집을 손으로 한 것과 같습니다. 고친 값도 허용 대상만 받습니다: 합칠 구간은 제안한 구간과 이웃 구간, 떼어 낼 구성요소는 그 구간의 것이고, 제안의 연산 종류는 바꿀 수 없습니다(연산 없이 받기만 됨).

**두 파일 사이에서 끊겼을 때.** 받아들이기는 구간 파일을 먼저 쓰고 제안 기록을 씁니다. 그 사이에서 끊기면(제안 기록 저장 실패 뒤 구간 복원도 실패, 또는 첫 저장 직후 종료) 화면이 알리고, 다음에 도면을 열 때 구간 이력의 `ai_review_accept`에 있는 제안을 제안 기록에서 '받음'으로 맞춥니다(`resynced` 표시, 결정한 사람은 비움).

**실측 전.** 구간 검토 호출을 실제 구독으로 잰 값은 아직 없습니다. 위 호출당 시간은 ⑤ 칸 분석 값을 빌린 추정입니다. SNP 6장(호출 3회) 실측은 사용자가 직접 돌립니다.

후속(이번에 하지 않음): 도면 위 제안 경계 점선, 제외 묶음의 조각(parts) 경계 보내기, 구간 검토 호출의 실제 시간 측정.

- 결론: §5.7의 gc 후속(unfreeze → collect → freeze)은 목표를 넘는 화면이 없어 필요하지 않다. 이번에는 코드를 고치지 않았다.

**S2 구현에서 바꾼 점.** '구간 분석에서 뺌' 표시는 등록 정보가 아니라 프로젝트마다 파일 하나(`work/data/study-nodes/<프로젝트>/구간제외도면.json`, `nodes.set_excluded`·`load_excluded`·`excluded_sheets`)에 도면번호로 적습니다. 등록 정보는 등록 판(registration_version)마다 고정된 기록이라 고치려면 다시 등록해야 하고, 도면번호로 적으면 다시 추출해도 이어지기 때문입니다. 표시는 ① 자료 등록 화면의 '구간 분석에서 빼기' 버튼으로 하고, 파일 이름·제목에 범례 낱말이 있으면 기록 보기에 제안만 보입니다. 표시를 바꿔도 저장된 검토구간은 그대로이고 ④에서 다시 제안할 때 반영됩니다. 도면번호는 프로젝트 그래프와 같은 규칙(공백 무시·대문자)으로 맞추고, 표시 파일을 읽지 못하면 ④·①·이전 스크립트가 그 사실을 보여 주고 뺀 도면을 말없이 다시 넣지 않습니다. 검토에서 경미로 넘긴 것: 앱 창 두 개가 같은 순간에 표시를 바꾸면 한쪽이 사라질 수 있음(검토구간 저장과 같은 한 사람 쓰기 가정), 같은 자료를 다른 도면번호로 다시 등록하고 다시 추출하지 않으면 표시가 그래프의 옛 번호에 닿지 않음.

**S5 구현.** `nodes.reopen`이 확정본의 구간 구성요소와 확정 열쇠(`study_nodes_ref`)를 `previous` 목록(최근 5개)에 덧붙이고, 편집·다시 제안이 그것을 물려줍니다. 결과를 이을 때는 결과의 확정 시각과 같은 기록을 찾으므로 여러 번 확정 해제해도 끊기지 않습니다. `hazop/study/remap.py`가 옛 구간마다 가장 많이 겹치는 새 구간을 대표로 정해 대응표를 만들고, ④ 다시 제안은 그 수와 함께 저장된 결과로 미리 옮겨 본 결과(막히면 그 사유)를 보이며 '이대로 적용'을 받고, 적용 전 저장본을 백업 폴더에 남깁니다. ④에서 다시 확정하면 바로 옛 결과를 칸 단위로 옮겨 저장합니다(옛 파일은 보관본). 그래서 ⑤를 열기 전에도 ⑥·탐색기가 같은 결과를 읽습니다. ⑤도 같은 함수를 부릅니다. 같음 구간은 칸 상태·항목을 그대로, 나머지는 항목에 '범위 바뀜'을 붙이고 칸 상태는 물려받지 않습니다. 그 사이 그래프 판이 바뀌었으면 판 이전 기록(kg_paths 이름 바꿈 포함)을 따르고, 기록 없이 내용이 바뀐 새 판이면 구성요소가 같아도 모두 '범위 바뀜'입니다. 사람이 판정한 항목이 '스크리닝 제외' 구간으로 가거나 옮길 곳이 없는 옛 칸이 있으면 옮기지 않고 사유를 보이며, ④에서 꺼낸 뒤 다시 확정하면 보관본에서도 찾아 옮깁니다. 설계 초안과 달리 같음 구간의 옛 ID를 다시 쓰지 않습니다(제안의 S1…Sn 연속 번호를 지키고, 결과는 구성요소 대응으로 이음). 옛 도면별 결과 이전(`span.migrate_results`)도 사람 판정 항목이 제외 구간으로 가면 멈춥니다(`to_excluded`).

**S3 구현.** ④ 구간 목록은 스크리닝 제외 구간을 기본으로 접고(머리글에 '제외 N개 접음(구성요소 M개)'), '스크리닝 ▾' 메뉴의 '스크리닝 제외 구간 보기'로 맨 아래에 펼칩니다(접힌 구간을 도면·탐색기에서 고르면 저절로 펼침). 꺼내기·떼기·제외로 옮기기도 같은 메뉴와 명령 팔레트에 있습니다(1366×768에서 구간 10개가 스크롤 없이 보이는 기준을 지키려고 버튼 줄을 늘리지 않음). 행 오른쪽 개수 앞에 등급(주요·일반·낮음·제외)을 보입니다. '꺼내기'는 구성요소 탭에서 고른 구성요소가 든 조각을(없으면 구간 전체를) 남긴 구간으로, '붙인 조각 떼기'는 규칙이 붙인 조각을 새 구간으로, '제외로 옮기기…'는 이유를 받아 제외로 바꿉니다(모두 사람 판정 `by: human`, 기록 `screen_override`). 제외 구간이 있으면 확정 전에 '도면 위에서 확인했습니까?'를 묻고, 기본 단추는 '아니요'입니다. 다시 제안하면 사람이 이유를 적어 내린 판정을 구성요소 기준으로 다시 얹습니다(꺼낸 조각은 같은 구성요소를 다시 꺼내고, 제외로 옮긴 구간은 구성요소가 같은 새 구간을 옮김). 맞출 곳이 없는 것만 수를 알립니다. 병합·분할 같은 구성 편집은 판정으로 세지 않습니다. 경계 한쪽이 나눈 자리면 '구간 나눔(Sx)'으로 보입니다(S2에서 넣음). 탐색기 ④ 묶음의 접기는 S4에서 ⑤와 함께 맞춥니다.

**S4 구현.** ⑤ 행렬의 행은 스크리닝 제외 구간을 빼고, 낮음 구간을 맨 아래에 모읍니다(행 머리 설명에 '스크리닝 낮음'). 머리글 KPI에 '스크리닝 제외 N개(④에서 확인)'를 보입니다. AI 일괄 실행·Excel 내보내기의 기본 범위와 탐색기 ⑤ 묶음도 같은 행을 씁니다(낮음 포함, D6). 결과 문서는 지금처럼 모든 구간의 칸을 두므로, 사람이 ④에서 꺼내면 행이 다시 생깁니다. 실패 칸 다시 실행·KPI·Excel 표지 수치도 행이 있는 구간만 셉니다. 제외 구간의 칸을 열려고 하면(명령 팔레트·관련 칸·④ '⑤ →') 열지 않고 ④에서 꺼내라고 알립니다. 구간 색은 ④와 같이 집합 순서로 정합니다. 남은 일: 탐색기 ④ 묶음의 제외 구간 접기, §4.5의 '낮음 빼기' 선택(지금은 낮음을 늘 포함).

**S1 검토에서 넘긴 일(2026-11-09).** S1 검토 1회(interrogate 두 갈래·Codex)에서 차단 지적(고리 배관 분할, 사람이 옮긴 구성요소의 판정, 새 필드 형식 검사, 여러 도면 계기 묶음, 기기를 품은 구간의 한쪽 경계)은 S1에서 고쳤습니다. 다음은 뒤 단위로 넘깁니다.
- S5(반영): 옛 도면별 결과가 `span.legacy_map`으로 '스크리닝 제외' 구간에 옮겨지는 경로(APR 5장 시험에서 사람 승인 항목 525개 중 416개)는 이제 이전을 멈춥니다.
- S3: 경로를 나눈 조각(배관·T에서 이웃 조각과 맞닿음)은 경계 한쪽이 비어 '끝: -'로 보입니다(SNP 29구간 중 6). ④·⑤ 머리에 '다음 구간 Sx로 이어짐'을 보입니다.
- 경미: 계기에 물리 연결(has_endpoint)이 있으면 이어지지 않은 두 배관 조각이 한 구간이 될 수 있습니다. 시험 자료에는 그런 계기가 없습니다.

- S1·S2·S5는 화면 파일을 거의 건드리지 않아 U3와 겹치지 않습니다. S5의 `screens/results.py` 수정은 `_load`의 빈 결과 분기 한 곳입니다.
- 성능 단위(N3 → N2 → N5 → N4)는 S1~S6과 파일이 겹치는 곳이 `hazop/app/explorer.py`·`screens/*.py`뿐이라, 구현 순서는 마스터가 U3 진행에 맞춰 정합니다. N3(`span.py`·`project.py`)은 S1~S6과 겹치지 않아 언제든 할 수 있습니다.

### A.8 확인하지 못한 것

- 측정 때 다른 세션 때문에 CPU 부하가 80~99%였습니다. 시간 값은 넓게 흔들리고, 같은 조건을 번갈아 돌려 범위를 함께 적었습니다.
- offscreen 측정이라 실제 창 그리기와 웹뷰(도면 SVG) 그리기 시간은 빠졌습니다. 실제 창 측정은 데스크톱 차례가 오면 `verify-hazop`으로 합니다.
- ⑤ 결과 저장본이 없는 상태(모든 칸 분석 전)에서 쟀습니다. 분석된 항목이 많으면 요약 비용이 더 커집니다(U3 메모와 같음).
- 스크리닝 판정의 '정답'은 없습니다. SNP는 도면별로 눈으로 확인했고(§3.2), APR1400은 구성 통계로만 봤습니다. 사람이 APR1400 한 계통(예: 9.2.2-1 기기냉각수 4장)을 직접 나눈 기준이 있으면 일치율을 잴 수 있습니다. 실제 위험을 놓치는지는 검증하지 않았습니다.
- U1은 34장만 다시 추출했습니다(디스크 여유가 9 GB라 143쪽 전체는 멈춤. 일괄 추출의 `path_expectations.json`이 도면당 16~200 MB, 143쪽 합 3.9 GB).
- 범례 낱말 제안(R0)이 다른 APR 도면을 잘못 집는지, 대응표 계산 시간은 재지 않았습니다.
- HAZOP 관행을 근거로 든 곳([일반지식])은 KOSHA·CCPS 원문을 확인하지 않았습니다.
