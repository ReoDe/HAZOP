- 발췌 생략: d10-04·d12-01·d43-01의 AI 해석 문장과 위험도 근거 문구는 넣지 않았고 화면에 "발췌 생략"으로 표시했습니다.

### 1.1 Qt 영역과 웹뷰 영역

[인터페이스.md §2.2](../../기획서/인터페이스.md)에 맞춰, 영역 경계 표시를 켜면 Qt 위젯은 회색 테두리와 `Qt · …` 꼬리표, 웹뷰는 진한 테두리와 `웹뷰 · …` 꼬리표로 보입니다.

- 웹뷰는 DOM 요소 하나를 ②④⑤ 화면의 캔버스 자리로 옮겨 씁니다(§2.2 "인스턴스 하나 공유").
- 웹 안의 떠 있는 패널은 레이어·줌·탭·근거 집계·강조 범례만 둡니다. ②에서는 웹 속성 패널을, ④⑤에서는 Qt 상세 패널을 씁니다.
- 노드 클릭(`nodeSelected`)과 강조 요청(`highlight`)은 상태줄 오른쪽에 메시지로 잠깐 보입니다.

## 2. 핵심 표현 규칙: AI 제안과 사람 확정의 구분

| 출처·상태 | 표현 | 적용 위치 |
| --- | --- | --- |
| AI 산출(해석·위험도 제안·원안) | **빗금 바탕** 상자, `[AI]` 표시가 붙은 배지, 위험도는 **속 빈 칩**(테두리만, "제안" 글자) | ④ 시나리오 카드, ⑤ 왼쪽 열 |
| 자동 판독(표제란)·규칙 산출(설계보완 후보 원안) | 빗금 바탕 + "자동 후보"·"원안" 배지(`[AI]` 표시 없음) | ① 메타데이터, ⑤ 설계보완 후보 |
| 사람 확정 | **흰 바탕 + 진한 실선 테두리** 상자, 검은 "확정" 배지, 위험도는 **채운 칩**("확정") | ⑤ 오른쪽 열, ① 확정 메타데이터 |
| 사람 입력 중(저장 전) | 채운 칩 + 파란 점선 외곽선, "저장 전" 글자 | ⑤ 위험도 계산값, 결정 칩 |
| 사람이 AI 제안을 채택 | 사람 확정 표현 + 출처 "사람(AI 제안 채택)" + "AI 값에서 가져옴 — 근거 확인 필요" 배지 | ⑤ 위험도 |
| 자동 지정(해당 없음) | 회색 "해당 없음" 결정 칩 + 상속 안내 띠 | ⑤ 설계보완 후보 |
| 미확인 | 호박색 "미확인" 글자 + 사유. 빈칸·0·"없음"으로 바꾸지 않음 | 전 화면 |
| 오류·차단 | 빨간 띠 또는 상자 + 다음 조치 | 전 화면 |

- 색만으로 구분하지 않고 바탕 무늬(빗금↔흰색)와 칩 모양(속 빔↔채움)을 함께 씁니다. 흑백으로 인쇄하거나 색각 이상이 있어도 구분됩니다 [추론].
- 위험도 등급은 사람이 직접 입력할 수 없습니다. 강도·빈도를 고르면 〈표5〉 조회 결과가 잠금 표시와 함께 나옵니다.
- 수용·수정에서 강도·빈도(와 각 근거)가 비면 저장되지 않습니다. AI 제안은 자동으로 복사하지 않고 **'AI 제안 가져오기'** 버튼을 눌러야 채워집니다. 이때 출처는 "사람(AI 제안 채택)"(`ai_proposal_adopted`)과 "AI 값에서 가져옴 — 근거 확인 필요" 배지로 표시하고, 직접 고르면 "사람(직접 선택)"(`human`)입니다.
- 강도 선택 옆에 "보호수단 효과를 반영하지 않음"을 표시합니다. 빈도 아래에는 "빈도를 낮출 때 인정한 보호수단" 목록을 두고, 확인 근거가 없는 보호수단(샘플은 모두 적정성·독립성 미확인)은 선택할 수 없게 막고 사유를 붙입니다.
- 원안은 패턴 원안과 AI 해석, 그래프에서 확인된 보호수단과 AI가 제시한 보호수단을 나눠 보여 줍니다.

## 4. 권고안 (§9 미결정 중 시안에서 정할 두 가지)

총괄이 사용자 위임으로 채택할 수 있도록 각각 하나로 정했습니다.

### 4.1 색 값

**권고**

| 항목 | 권고 값 | 모양(색과 함께 쓰는 단서) |
| --- | --- | --- |
| 원인 설비 | `#dc2626` (빨강, 현재 `--selected`와 같음) | 심볼 **채움**(30%) + 굵은 테두리 |
| 경로 | `#ea580c` (주황, 현재 경로 강조와 같음) | 배관·관계 **굵은 선**(5px). 강조 중에는 나머지 오버레이를 16% 불투명도로 흐림 |
| 보호수단 | **`#c026d3`** (자홍, 신규) | **이중 테두리 + "보호수단" 배지**. 그래프에서 세지 않은 보호수단은 홑 테두리 + "보호수단 · 미계수" 흰 배지 |
| 추정 경로 | 경로색과 같은 주황 | **파선**(9·6). 범례에 "실제 흐름 경로 아님" |
| 밸브 노드 | **`#0f766e`** (청록) | UI 파랑 `#2563eb`과 분리 |
| 선택(클릭) 노드 | UI 파랑 `--ui` 테두리 | 원인 빨강과 분리 |
| 위험도 등급 | 색을 쓰되 **〈표9〉 허용 구분 3단**으로만: 1·2 수용 = 회색, 3·4 조건부 수용 = 호박, 5 불허 = 짙은 빨강. 숫자와 등급명(〈표6〉)은 항상 함께 표시 | AI 제안은 속 빈 칩, 사람 확정은 채운 칩 |

**이유**

1. 원인·경로는 현재 코드(`template.html`의 `--selected`, `.onpath`)에 이미 있는 값이라 그대로 쓰면 바꿀 곳이 적습니다. 보호수단만 새 색이 필요했고, 노드·관계 색(파랑·청록·하늘·남색·초록·보라·호박·빨강·주황)과 겹치지 않는 색상 영역이 자홍뿐이었습니다 [추론].
2. 빨강·주황·자홍은 색각 이상에서 헷갈릴 수 있습니다 [일반지식]. 그래서 세 강조를 "채움 / 굵은 선 / 이중 테두리+배지"로 모양부터 다르게 했고, 색은 보조 단서로만 씁니다.
3. 밸브가 `--ui`와 같은 값이면 "선택된 것"과 "밸브"를 구분할 수 없습니다. 청록은 노드 색 중 비어 있는 색상이고, 초록 배관(`#16a34a`)보다 어둡고 푸르러 배관 위에 놓여도 구분됩니다 [추론].
4. 클릭 선택을 빨강으로 두면 원인 설비 강조와 겹칩니다. 선택은 UI 상태이므로 UI 강조색(파랑) 하나로 표현하는 원칙과도 맞습니다. 이 변경은 ②의 기존 뷰어 선택색(빨강)도 바꾸는 것이므로 구현 시 `template.html` 수정이 필요합니다.
5. 위험도 5단계에 모두 다른 색을 주면 색이 너무 많아지고 "UI 강조는 파랑 하나" 원칙과 충돌합니다. 설계보완 후보 발생 조건(`risk_conditional_or_worse`)이 바로 "조건부 수용 이상"이므로, 같은 경계로 색을 나누면 목록에서 설계보완 대상이 한눈에 보입니다. 다만 〈표9〉 비고 칸을 허용 여부로 해석한 것 자체가 [추론](HAZOP기법지침 §6)입니다.

**남는 약점**: 장비 색 `#1d4ed8`도 UI 파랑과 가깝습니다(이번 결정 범위 밖). 경로 주황과 계측 연결 호박(`#d67506`, W5에서 조정됨(D7))이 비슷하지만, 강조 중에는 나머지를 흐리게 하므로 실제로 함께 보이는 일은 적습니다 [추론].

### 4.2 근거 집계의 '추정 경로' 분류 기준

**권고**: 근거 관계 중 **배관 끝점 관계(`has_endpoint`)이면서, 그 배관 구간이 분석 당시 그래프(`<실행 폴더>/inputs/graph.json`)에서 `flow_direction`이 없는 것**을 추정 경로로 셉니다. 그 배관 구간 노드(`entity-seg-*`) ID도 같은 기준을 따릅니다. 같은 사실은 `analysis.json`의 `explorations[].reached[].segment_flow[].flow == "unknown"`으로도 확인할 수 있습니다.

다음은 추정 경로가 **아닙니다**(도면 표시로 셈).

| 경우 | 판정 필드 | 이유 |
| --- | --- | --- |
| 흐름 반대로 거슬러 간 경로 | `segment_flow[].flow == "against_flow"`, `direction_from_start: upstream` | 방향이 확인된 실제 배관입니다. 탐색 방향만 반대입니다 |
| 닫힌 밸브를 지나는 경로 | `path_context.valve_state: closed_valve_on_path` | 배관은 실제로 있고, 정상 운전 시 흐름이 없다는 사실은 카드의 경로 문맥 문구로 보여 줍니다 |
| 신호·계측 연결 | `path_context.material_flow_path: false` | 도면에 그려진 연결이며 흐름 방향 개념이 없습니다 |

**근거 집계 계산 규칙** (시안에 구현한 방식)

- N = 아래 ID의 고유 개수: `cause_equipment` + 보호수단 `node_id` + `graph_evidence.node_ids`·`relation_ids` + `ai_interpretation.node_ids`·`relation_ids` + 노드를 가리키지 않는 근거 ID(`ev-node-*`, `ev-path-*`가 아닌 것, 예: `ev-design-intent`) + 그 시나리오를 범위로 하는 보류(`holds[].scope == scenario_id`).
- 분류 순서: ① 도면에 그릴 요소가 없거나 웹이 `highlightResult`로 못 그렸다고 알린 ID, 그래프 버전 불일치일 때의 모든 ID → **미표시** ② 위 기준에 맞는 관계·구간 → **추정 경로** ③ 나머지 → **도면 표시**. 각 ID는 한 번만 셉니다.
- 예: d09-04는 "근거 7 중 도면 표시 7 · 추정 경로 0 · 미표시 0", d10-01은 "근거 4 중 도면 표시 2 · 추정 경로 0 · 미표시 2"(미표시 = 보류 hold-013·hold-038)입니다.

**이유**

1. 판정 근거가 이미 결정적으로 계산되어 있습니다. 경로 엔진(`hazopPathEngine`의 `segments_direction_unknown`)과 뷰어 CSS(`.onpath.dirunknown` 파선)가 같은 기준을 쓰므로, 화면·검사·경로 질의가 한 기준으로 맞춰집니다.
2. 인터페이스.md §3.3 강조 규칙("흐름 방향이 확인되지 않은 배관 구간이 포함된 관계 → 파선")과 문장 그대로 일치합니다.
3. 데모의 "추정선 (파선 — 실제 배관 경로 아님)"은 "도면에 실제로 확인된 흐름이 아닌 선"이라는 뜻입니다. 흐름 반대·닫힌 밸브·신호선까지 넣으면 실제로 그려진 배관을 "추정"이라 부르게 되어 근거의 신뢰도를 낮춰 보이게 합니다 [추론].

**확인할 점**: 현재 샘플 그래프는 11개 배관 구간 모두 흐름 방향이 있어(`segments_without_flow: []`) 추정 경로가 항상 0입니다. 파선 표현은 "시안 상태 예시 → 추정 경로 가상 예시"(RC-L011 `entity-seg-005`를 미확인으로 가정)로만 볼 수 있습니다.
